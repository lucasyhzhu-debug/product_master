Frollie CRM — Design Principles & Reference Screens

Principles ① Record = hub ② Linking model ③ Timeline (recommended) ④ Object page ⑤ Taxonomy

A proof of the CRM information model — not pixels. We review our linking, data model, and taxonomy against record-centric CRMs (Salesforce Lightning, HubSpot, Attio, Intercom, Stripe, Linear), distil principles, and show reference screens that embody them. Comment on the model (what links to what, what the timeline event shape is, how things are grouped). Once agreed, a workflow applies these across the D/E specs before planning.

The principles

10 rules, 4 themes

ANavigation & linking
A1Every entity has one canonical page, always rendered as a link
Customer, subscription, week, invoice, order, agreement, payment, activity — each a stable route. A reference to it is always a link to it, never inert text.
Lineage: Salesforce/Attio record-centric
A2Breadcrumbs mirror the object hierarchy, not click-history
`CRM › Customers › Amsterdamn › Dubai Chewy › Wk 23 Jun › INV-2606-014`. A deep-link resolves the full trail; each segment links to its parent.
Lineage: Stripe dashboard, Linear
A3The customer record is a hub/router, not a scroll-dump
At-a-glance state (credit, status) + cards that link OUT to object pages. Detail lives on the object's own page, reached in one click.
Lineage: HubSpot record, Attio
A4Cross-object links are bidirectional
Agreement ↔ subscriptions, invoice ↔ week ↔ orders, order ↔ scheduler. Every object shows its back-references ("linked subscriptions", "orders this week").
Lineage: Salesforce related-lists
BData model & taxonomy
B5Timeline = derived union over a normalized event log
One `customerActivity` shape with polymorphic subject-refs; domain events (orders/invoices/ledger) projected into the same shape. Model once; render as feed / log / statement.
Lineage: Salesforce activity, Stripe events
B6One shared activity taxonomy, sourced once
`type · direction · actor · icon · color` defined in a single `crmActivityTaxonomy` map (like `platformColors.ts`) and reused across timeline, dashboard, kanban, invoice.
Lineage: design-system tokens
B7"What happened" ≠ "what's next"
Past activity is a feed; upcoming obligations (invoice due, contract end) are pinned tasks above it — never interleaved as if they already happened.
Lineage: HubSpot upcoming vs activity
B8Facets are indexed fields, not client filters
Filter by type/actor/direction/window on the server via indexes, so the log stays queryable at scale and counts are real.
Lineage: Salesforce/Linear faceting
CDensity & money
C9Compact by default, progressive disclosure, windowed loads
14-day window default, expand a row for detail, "load older" extends. Don't pre-render a customer's entire history.
Lineage: Salesforce Lightning collapse
C10Money is first-class and traceable
Finance events show a signed delta + running balance + a link to the ledger/invoice. Integer IDR. Read the derived `pool` (source of truth), never re-key a total.
Lineage: Stripe balance, our ledger invariant
DAccess & states
D11Strip, don't hide
Confidential fields (partner price, credit) are omitted server-side per role — never client-side hidden (leaks) and never via a manager-only query on a staff-reachable surface (crashes on mount, Pitfall #19).
Lineage: our Pitfall #19 + kanban gap #2
D12Designed empty / loading / error states everywhere
"No activity in 14 days", "No subscriptions yet", loading guards, and actionable errors — every CRM surface, not an afterthought.
Lineage: Intercom/Linear empty states

② The linking model · principles A1 A2 A4

Object hierarchy + bidirectional links

Breadcrumbs follow this hierarchy; every node is a page; arrows that point both ways are the back-references each object must render.

Indigo = strong hierarchy (breadcrumb path, A2). Grey = reference edge (the activity log + agreement attach to the customer). Every edge is navigable both ways (A4): an invoice links up to its week + down to its orders; a week lists its orders + its invoice + its ledger entries. The activity log is a projection of all these events, not a sibling object (B5).
③ Recommended timeline · principles B5 B6 B7 C9 C10

The synthesis: log model, feed view, finance balance

Data model = v3 (normalized queryable event log + facets) · default view = v2 (day-grouped feed) · finance affordance = v1 (running balance on money rows). One contract, the most readable default, plus the balance where it matters.

The gaps, in detail — (1) B5: the timeline's logged half (WhatsApp, manual milestones) has no base table; derived events project from existing tables but logged ones need customerActivity {customerId, type, subtype?, direction, actor, occurredAt, subjectRefs, summary}. (2) B6: event type→icon/color/direction isn't centralized — create src/lib/crmActivityTaxonomy.ts (one icon per type + per-subtype overrides like ✓ funded / ⚖ reconcile), the validator for customerActivity.type and the source for every disc/badge across timeline, dashboard, kanban, invoice. (3) B8: facets must be indexed fields, so customerActivity needs by_customer_occurredAt (windowed feed) + type/actor/direction support — else faceting is client-side. (4) A1/A4/B8 — confirmed `schema.ts:2287–2344`: invoices has no customerId and only by_order/by_status_number/by_date — a customer-scoped invoice lookup (CRM home funding list, timeline invoice events) must traverse order→customer or week→subscription→customer. Add a denormalized customerId + by_customer (additive); by_subscriptionWeek is already planned in Phase B.
