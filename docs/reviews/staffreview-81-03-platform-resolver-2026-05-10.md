### Improvement 1: `linkedMenuProductId` lookup path will fail type-check or silently dead-code

**Verified facts:**
- `convex/schema.ts:93-118` defines `menuProducts` table — fields are `code`, `name`, `grams`, `defaultPrice`, `isActive`, `unitCost`, `cachedProductionSummary`, `posSlot`, `unitCostStaleAt`, `packagingPosSlot`, `productType`, `productionType`, `productionUnits`, `isFixed` (and others below). **No `source` field.** The plan's NOTE in Task 3.1 (line 350) flags this correctly — but the implementation still ships the lookup code:
  ```typescript
  if (row.linkedMenuProductId && ctx) {
    return (async () => {
      const product = await ctx.db.get(row.linkedMenuProductId!);
      if (product?.source && product.source !== "bigseller") { ... }
      ...
    })();
  }
  ```
- `Doc<"menuProducts">` type generated by Convex will not have a `source` property → `product?.source` is `unknown` or `never` access. Either type-check fails OR (if `as any` somewhere) the branch never executes. Test 10 is correctly `it.skipIf(true)` so the issue isn't caught at test-time.

**Why it matters:**
The plan's `must_haves.truths` line 4 says "BigSeller fallback: underlyingSource (if present) → linkedMenuProductId.source lookup → 'BigSeller' transitional" — the middle path is documented as active. Shipping dead code that *looks* active but isn't makes the next maintainer think the path works and write code that depends on it.

**Recommendation:**
Pick one of:
- **(A) Remove the dead path entirely** — until the schema field lands, only the underlyingSource (D-03 forward-compat) and transitional fallback paths exist. Add a comment: `// linkedMenuProductId.source lookup deferred until menuProducts.source field lands (see ADR-0001)`. Update `must_haves.truths` line 4 to remove the middle path. Drop the `ctx?: QueryCtx` parameter (no longer needed today). Re-add when the schema field ships.
- **(B) Keep the path with explicit type-system escape hatch** — change the type lookup to `(product as { source?: string } | null)?.source` and add a runtime check + comment explaining this is forward-compat for the schema field. Acceptable but uglier.

**Recommended:** (A). Cleaner, fewer moving parts, and the ESLint guard + ADR-0001 reference still mechanically prevent regression. Test 10 stays skipped with a comment pointing to the ADR; un-skip when the schema field lands.

## 4. Refinements (Minor Suggestions)

- **R1 — `platformDisplay()` is identity-on-literal at every callsite.** Migration pattern `platformDisplay(resolvePlatform({source: s}).platform)` is functionally equivalent to `resolvePlatform({source: s}).platform` since `platformDisplay` is `(p) => p`. The forward-compat chokepoint is preserved by the *export*, not by every call. Optional simplification: drop `platformDisplay()` from migration patterns (Tasks 3.3, 3.5) and use `.platform` directly. Keep `platformDisplay` in the module so the export-shape is stable for future i18n. Saves ~12 redundant function calls without losing the chokepoint.

- **R2 — Task 3.4 step 4 placeholder source value is suboptimally documented.** `resolvePlatform({ source: "internal", orderChannel: o.channel }).platform` — the `source: "internal"` is a placeholder that the orderChannel branch ignores. The JSDoc on `ResolvePlatformRow` could be tightened: rename `source` to `source?` (optional) and treat orderChannel-only calls as: `resolvePlatform({ orderChannel: o.channel })`. Cleaner contract; today's required-source signature reads as "orderChannel is a modifier" rather than "orderChannel can be the only signal."
