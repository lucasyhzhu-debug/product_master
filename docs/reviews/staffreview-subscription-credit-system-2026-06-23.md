## 1. Summary

**Overall Assessment:** Revise (then approve for planning)

The design is coherent and the core invariant (`schedule = invoice = credit`) is the right spine. The §13 resolutions (bounded rollover, deposit-reuse) are sound and reduce surface area. **One architectural cluster blocks clean planning: the existing invoice model is strictly 1-invoice-↔-1-order, but the weekly subscription invoice must represent a week covering many daily orders.** The spec's §4.5 describes the *intent* but not the two concrete schema changes it forces (`orderId` → optional, `items[].date`) nor that a *new* invoice builder is needed (the current one reads `orderItems`, which a weekly invoice has none of). Address that cluster + 5 improvements and this is ready for `writing-plans`.

## 2. Critical Issues (Must Fix)

| # | Issue | Category | Location |
|---|-------|----------|----------|
| C1 | Weekly subscription invoice contradicts the 1:1 invoice↔order model; `orderId` is required, builder reads `orderItems` | Schema / Logic | spec §4.5 vs `convex/schema.ts:2265`, `convex/invoices/mutations.ts:145,372` |
| C2 | `invoices.items` object has no `date` field; per-delivery-day lines impossible as-is | Schema | spec §4.5 vs `convex/schema.ts:2287-2293` |

### Issue C1: Weekly invoice ≠ existing single-order invoice model

`invoices.orderId` is **required** (`v.id("orders")`, `convex/schema.ts:2265`) and the whole flow is single-order: `createDraft({ orderId })` (`mutations.ts:145`) loads one order, builds `items` from that order's `orderItems` (by_order index), and `finalize` (`mutations.ts:372`) assigns the `INV-YYMM-NNN` number via `getNextInvoiceNumber`/`invoiceCounters`. A **weekly subscription invoice covers 7 days × possibly multiple orders and has no single owning order** — and at confirm-time the daily orders may not even exist yet (they're generated by the same Confirm action). §4.5 says "lets ONE invoice represent a week's credit covering MANY orders" but does not state the schema/flow changes that requires.

**Recommendation (fold into §4.5):**
- Make `invoices.orderId` **optional** (`v.optional(v.id("orders"))`). Existing standard invoices keep it; subscription-weekly/top-up invoices leave it null and rely on `subscriptionWeekId`.
- Keep the existing `createDraft`/`finalize` path **untouched** for standard order invoices. Add a **separate builder** `createSubscriptionWeeklyInvoice({ subscriptionWeekId })` that builds `items` from `subscriptionWeeks.plannedDays` (NOT from `orderItems`), reuses `getNextInvoiceNumber` for the `INV-YYMM-NNN` series, and sets `invoiceKind: "subscription_weekly"`.
- Guard the existing `by_order` query consumers: anything assuming `invoice.orderId` is non-null must tolerate null (grep `invoice.orderId` / `.withIndex("by_order"` before merge).

### Issue C2: `items` object needs a `date`

`invoices.items` = `{ productName, variant?, qty, unitPrice, lineTotal }` (`schema.ts:2287-2293`) — no date. The visual day-by-day invoice (mockup §⑦) groups lines under dates. Add `date: v.optional(v.number())` to the `items` object (optional preserves all existing standard invoices). The visual invoice groups/sorts by `date`; standard invoices (date null) render flat as today.

### Improvement I1: Price field name
`menuProducts.defaultPrice: v.number()` is the actual field (`convex/schema.ts`). §6 ("unit price defaults from the product") and `scheduleTemplate` should state: default = `menuProducts.defaultPrice`, overridden by `subscriptions.unitPrice` (confidential). Naming it stops the planner guessing `price`/`unitPrice`.

### Improvement I2: Missing baseline/weekly-qty fields
§2 (clauses 1–2), §4.6 (agreement key-terms snapshot), and §11 (above-baseline → `needsSupplierConfirmation`) all reference baseline and weekly volume, but §4.1 `subscriptions` has neither. Add `baselineDailyQty: number` (drives the above-baseline comparison) and `weeklyQty: number` (or derive from `scheduleTemplate`; if derived, say so). Without `baselineDailyQty` on the row, §11's enforcement has nothing to compare against.

### Improvement I3: Subscription orders & analytics pollution
§4.4 reuses `orders`/`orderItems`. Two consequences to specify:
1. The subscription order's `orderItems` must carry the **partner `unitPrice`** so `orders.totalAmount` (DERIVED sum of `orderItems.lineTotal`, `schema.ts`) equals the credit drawdown (`qty × unitPrice`). Otherwise the drawdown and the order total diverge.
2. **1,050 pcs/wk at a confidential B2B price will land in the existing sales/margin/channel reports** unless excluded. Specify how subscription revenue is tagged (e.g. `fundingSource`/`subscriptionId` filter) and whether it's excluded or bucketed separately in `/financials` + channel analytics — and confirm BOM ball-counting (CLAUDE.md Pitfall #11/#13) still resolves for these products. This is the highest-risk silent side effect.

### Improvement I4: Reuse the resilient send helper
§9 says "resilient + watchdog (`*Resilient` + 15-min watchdog)". Name the existing implementation (the `convex/telegram/salesSummary/` send pattern + the transient-retry fix from PR #175) so Phase E reuses it rather than re-rolling. Also follow Pitfall #21 (extend `KNOWN_TELEGRAM_ROLES` with `"subscription-ops"`, no new env var) and Pitfall #22 (every new command needs a `COMMAND_POLICY` entry).

### Improvement I5: Access-control trap
§10 already cites Pitfall #19 — good. Keep it as an explicit, per-phase Verification line: code-auditor greps every new `protectedQuery`/`protectedMutation` `roles` and confirms it is a superset of the `/crm` route's `requiredPermission` (a `useSessionQuery` subscribes on mount, before any dialog opens — a manager hitting an `["admin"]`-only query throws a generic Server Error page).

## 11. Edge Cases to Address

- [ ] Confirm action generates orders **and** the weekly invoice atomically (partial failure = orphan orders or orphan invoice).
- [ ] Top-up delta when schedule is edited *down* (negative delta — refund or no-op? spec implies top-ups only).
- [ ] Order generated for a day whose product was later removed from `menuProducts`.
- [ ] Drawdown when partner `unitPrice` changed mid-week (snapshot price on the week, not live).
- [ ] Rollover credit FIFO across a subscription that changes `unitPrice` between weeks.
- [ ] Manager opens a CRM query before a dialog opens (Pitfall #19) — roles must be route-superset.
