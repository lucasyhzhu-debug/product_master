Create `tests/convex/ballDistribution.test.ts` with comprehensive test coverage using fixture-based AAA pattern from RESEARCH.md.

**Test structure (25 tests in 5 describe blocks):**

**1. Priority ordering (5 tests):**
- Allocates to earliest deadline order first (2 orders, 1 has earlier dueDate, insufficient balls for both)
- Handles same deadline by order creation time
- Confirmed orders get priority over InProduction orders with same deadline
- Multiple orders with different deadlines get correct sequence
- Empty queue handles new balls correctly

**2. Partial fills (6 tests):**
- Order needing 100 balls gets 60 now, 40 later across multiple batches
- Partial fill maintains unitsRemaining correctly in orderItemProduction
- Multiple partial fills accumulate correctly
- Order transitions to InProduction on first partial fill
- Order transitions to complete (auto-transitions per statusTransitions.ts) when fully filled
- Tray exhaustion mid-order leaves remaining orders unfilled

**3. Mixed ball types (5 tests):**
- Order with 2 products (1 BIG_BALL, 1 MID_BALL) distributes correctly
- Order with 3-4 products distributes correct type to each
- BIG_BALL production only fills BIG_BALL needs, leaves MID_BALL unfilled
- MID_BALL production only fills MID_BALL needs, leaves BIG_BALL unfilled
- Complex order (mixed types) with partial fill preserves correct unitsRemaining per type

**4. Ghost ball prevention (5 tests):**
- Balls produced with no pending orders sit in holding state (NOT orphaned)
- After distribution to all orders, excess balls are traceable (verifyNoGhostBalls passes)
- Cancelled order during production releases balls back to holding
- Production pipeline stages (produced → packaged → to-sticker → stickered) all maintain traceability
- Verify sum of allocated + holding = total produced

**5. Auto-transitions (4 tests):**
- Confirmed order auto-transitions to InProduction on first ball filled
- InProduction order stays InProduction on partial fill
- InProduction order auto-transitions to next status when production complete (per statusTransitions.ts)
- Invalid status (e.g., Draft) does NOT get balls allocated

**Implementation notes:**
- Use `convexTest(schema)` for isolated DB per test

- Each test: Arrange (create orders/products), Act (add balls), Assert (verify allocation + status + traceability)
- Follow existing test pattern from tests/convex/orders.test.ts (imports, structure, assertions)

**Known failure scenarios to cover (from CONTEXT.md):**
- Ghost balls: Verify with verifyNoGhostBalls helper
- Ball allocation errors: Assert ballType matches productionUnitCode, quantities match unitsRemaining
- Order status issues: Verify auto-transitions after each addBallsToTray call

Use realistic Frollie data: under 10 product types, 10-50 balls per scenario, deadline-based priority.
