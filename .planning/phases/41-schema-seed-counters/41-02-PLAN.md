**Create `convex/lib/counter.ts`:**

```typescript
import type { MutationCtx } from "../_generated/server";
import { getWibComponents } from "./periodRange";
```

Export two functions:

1. **`formatCounterNumber(prefix: string, dateStr: string, sequence: number): string`** (pure, exported for testing)
   - Returns `${prefix}-${dateStr}-${String(sequence).padStart(3, "0")}`
   - This is the testable pure function

2. **`getNextNumber(ctx: MutationCtx, prefix: string, now?: number): Promise<string>`** (async, exported for use by mutations)
   - Accept optional `now` parameter for testability (defaults to `Date.now()`), matching `calculatePeriodRange` pattern in periodRange.ts
   - Get WIB date components: `const { month, day } = getWibComponents(now ?? Date.now())`
   - Format dateStr: `${String(month + 1).padStart(2, "0")}${String(day).padStart(2, "0")}` (month is 0-indexed from getWibComponents, so +1)
   - Query counters table: `ctx.db.query("counters").withIndex("by_prefix_date", q => q.eq("prefix", prefix).eq("date", dateStr)).unique()`  // MUST use .unique() not .first() — .unique() throws on duplicate rows, preventing silent counter corruption
   - If counter exists: `sequence = counter.lastSequence + 1`, then `ctx.db.patch(counter._id, { lastSequence: sequence })`
   - If counter does not exist: `sequence = 1`, then `ctx.db.insert("counters", { prefix, date: dateStr, lastSequence: sequence })`
   - Return `formatCounterNumber(prefix, dateStr, sequence)`
   - Convex OCC guarantees atomicity -- no manual locking needed. If two mutations race on the same counter row, one will automatically retry.

CRITICAL: Use `getWibComponents(now ?? Date.now())` NOT `new Date()` for date extraction. The `getWibComponents` function applies +7 hour WIB offset before extracting month/day. Using `new Date()` would give UTC date which is 7 hours behind WIB.

NOTE on `getWibDateStr`: This helper extracts MMDD from `getWibComponents` and delegates to it for WIB offset math. It does NOT duplicate the WIB logic in `periodRange.ts` — it is a thin wrapper that formats the output as MMDD string.

NOTE on counter table year boundary: The `counters.date` field stores MMDD without year. On Jan 1 of a new year, the counter row for "0101" from the prior year (if still present) would continue incrementing rather than resetting. This is acceptable because ~1,095 rows/year is negligible and old counter rows don't affect correctness (the sequence just continues from a higher number). Document this in a code comment.

**Create `convex/lib/__tests__/counter.test.ts`:**

Test the pure `formatCounterNumber` function and WIB date logic:

1. **Format tests:**

   - `formatCounterNumber("JE", "0312", 42)` returns `"JE-0312-042"`
   - `formatCounterNumber("RMB", "0101", 999)` returns `"RMB-0101-999"`

2. **WIB date string tests** (test the date formatting logic directly):
   - Export a helper `getWibDateStr(utcMs: number): string` from counter.ts that extracts MMDD from `getWibComponents`
   - At 2026-03-12 01:00 WIB (= March 11 18:00 UTC): returns "0312" (WIB date is March 12)
   - At 2026-03-12 00:00 WIB (= March 11 17:00 UTC): returns "0312" (WIB midnight = still March 12 WIB)
   - At 2026-03-11 23:59 WIB (= March 11 16:59 UTC): returns "0311" (still March 11 WIB)
   - At 2026-01-01 00:00 WIB (= Dec 31 17:00 UTC): returns "0101" (year boundary)
   - At 2026-12-31 23:59 WIB: returns "1231"

3. **Edge case tests:**
   - Sequence 0 pads to "000" (edge case, shouldn't happen in practice)
   - Sequence 1000+ still formats correctly (no truncation): `formatCounterNumber("EXP", "0312", 1000)` returns `"EXP-0312-1000"`

Note: The `getNextNumber` function requires `MutationCtx` (Convex database context) and cannot be unit-tested without convex-test infrastructure. Its atomicity is guaranteed by Convex OCC. The pure formatting and WIB date logic are what we test here.
