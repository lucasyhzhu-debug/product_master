# Phase 80.1: Code Review Report

**Reviewed:** 2026-04-18T00:00:00Z
**Depth:** standard
**Files Reviewed:** 20
**Status:** issues_found

## Summary

Phase 80.1 consolidates 11 per-widget Convex queries into 3 snapshot queries (`kpiAndChannelSnapshot`, `timeSeriesSnapshot`, `skuSnapshot`) backed by 10 pure reducers, ships a shared `chartPrimitives.tsx` library, and migrates 2 heatmaps from Recharts to `@nivo/heatmap`. The architecture is sound and the test coverage is strong (reducer unit tests, integration tests, DI call-count assertions, and a 500-order runtime budget test). No critical security or data-loss issues found.

Four warnings and five info items are noted below. The most impactful are:
- **WR-01**: `reduceByWeekdayRolling` has a quadratic O(N²) label membership check (`labels.includes(k)`) on lines 765–766 that could degrade at high order volumes.
- **WR-02**: `useSkuPareto` slices `skuTop.rows` before the caller, discarding the `totalRevenue` from the snapshot; `SkuParetoChart` recomputes cumulative % over the sliced subset rather than the full window, producing inflated cumulative percentages when `topN < skuTop.rows.length`.
- **WR-03**: `DayHourHeatmap` calls `useMemo` before the early-return `undefined` guard, violating React hooks ordering rules and risking a runtime error.
- **WR-04**: `SkuChannelHeatmap` always renders `data.matrix` rows from the snapshot (capped at `SKU_SNAPSHOT_TOP_CAP=20`) even though the `topN` prop is also sliced in `useSkuChannelMatrix`. The `transformed` memo runs on the pre-`topN`-sliced `data.matrix`, but the chart is rendered after the `topN`-sliced `data` guard — this is inconsistent but not currently broken because the hook slices before returning.

## Warnings

### WR-01: Quadratic label membership check in `reduceByWeekdayRolling`

**File:** `convex/reports/unitEconomics.ts:765-766`
**Issue:** After building the calendar-day label range, orphan keys from `orderCountByDay` and `unitCountByDay` are deduplicated with `labels.includes(k)` — an O(N) scan inside a loop, making the whole block O(N²) in the number of distinct order days. For sparse external-revenue windows with thousands of distinct transaction dates this grows non-linearly.
**Fix:**
```typescript
// Replace the includes() loop with a Set-based check:
const labelSet = new Set(labels);
for (const k of orderCountByDay.keys()) if (!labelSet.has(k)) labels.push(k);
for (const k of unitCountByDay.keys()) if (!labelSet.has(k)) labels.push(k);
```

### WR-02: `useSkuPareto` slices rows before returning — cumulative % in `SkuParetoChart` is over the sliced subset, not the full window

**File:** `src/hooks/convex/useAnalytics.ts:59-60` and `src/components/analytics/SkuParetoChart.tsx:35-48`
**Issue:** `useSkuPareto(topN)` returns `skuTop.rows.slice(0, topN)`. `SkuParetoChart` then recomputes `totalRevenue` and `cumulativePct` over that sliced array. When the snapshot contains more than `topN` rows (including an "Other" row the reducer appended), the cumulative % is inflated — it will reach 100% at the visible top-N even though those products don't represent 100% of revenue. The snapshot already computes correct `cumulativePct` values relative to the full window; the client recomputes them incorrectly over the slice.

The "Other" row (appended by `reduceSkuTop` when items exceed the cap) is always present in the snapshot when there are more than `SKU_SNAPSHOT_TOP_CAP=20` products. `useSkuPareto(10)` slices to 10 rows, throwing away the "Other" row — so the chart's Pareto line does not reach 100%.

**Fix:** Remove the client-side cumulative recomputation and use the snapshot's precomputed `cumulativePct` values directly. If client-side slicing is needed, use the snapshot's `totalRevenue` (not a recomputed total from the slice):
```typescript
// In SkuParetoChart — do not recompute, use server values:
const withCumulative = data.map((d) => ({
  ...d,
  displayName: truncateWithTooltip(d.name, 22).display,
  fullName: d.name,
  // cumulativePct already correct from server
}));
```
And in `useSkuPareto`, expose `totalRevenue` alongside the rows so the chart can optionally display it.

### WR-03: React hooks ordering violation in `DayHourHeatmap` — `useMemo` called before conditional return

**File:** `src/components/analytics/DayHourHeatmap.tsx:43-64`
**Issue:** `useMemo` is called on line 43, then the component returns early with a loading skeleton on line 58 when `data === undefined`. This is a hooks ordering violation: React requires all hooks to execute in the same order on every render. The `useMemo` on line 43 runs during the loading state (when `data` is undefined), but that is actually fine for the `useMemo` call itself since it guards `if (!data) return []`. The real problem is that linters and strict-mode React will flag this as a violation of the "no hooks after conditional return" rule — however here the hook is **before** the return, so this is actually acceptable per React rules. 

Re-examining: `useMemo` at line 43 is called unconditionally before the `if (data === undefined)` early return at line 58. This is correct hook ordering (hook before conditional). The `useMemo` itself handles the `!data` case by returning `[]`. This is valid React.

**Correction:** WR-03 is a false positive on careful re-read. The hook is unconditionally called at line 43 before any conditional returns. This is correct. Downgrading to Info.

### WR-03 (revised): `reduceTypeMixOverTime` has an asymmetric early-exit that bypasses `reduceVolumeByType`'s own empty-state handling

**File:** `convex/reports/unitEconomics.ts:895-899`
**Issue:** `reduceTypeMixOverTime` early-returns `{ buckets: [], series: [] }` when `current.orders.length === 0`, but `reduceVolumeByType` (which it delegates to) handles empty items gracefully anyway — the Map is empty, `sortedBuckets` is `[]`, and `series` maps over `pre.typeCodes` returning all-zero value arrays. The early exit produces a structurally different shape: `series: []` vs `series: [{ code, name, values: [] }, ...]`. This means `TypeMixOverTime.tsx` gets an empty `series` array when there are no orders, so no `<Bar>` elements render (correct behavior), but any consumer iterating `data.series` to build a legend would see zero entries. This is a shape inconsistency between the empty-state and the populated-state responses for the same field.
**Fix:** Remove the early-exit guard and let `reduceVolumeByType` handle the empty case:
```typescript
export function reduceTypeMixOverTime(
  current: WindowData,
  pre: Precomputed,
  granularity: "day" | "week",
) {
  return reduceVolumeByType(current, pre, granularity);
}
```
`reduceVolumeByType` already returns `{ buckets: [], series: [{ code, name, values: [] }...] }` when items is empty — consistent shape with the non-empty case.

### WR-04: `loadExternalStream` 31-day lookback constant is an undocumented magic number

**File:** `convex/reports/unitEconomics.ts:141`
**Issue:** `const scanFrom = args.fromTs - 31 * 86400000` uses a hardcoded 31-day lookback with no named constant or explanation beyond the inline comment. The comment says "allow 31-day lookback for rows using transactionDate<<periodStart" — this is sound reasoning, but the number is a magic constant. If someone changes the lookback window for performance, they might not find this. This is minor (info-level) but worth noting.
**Fix:** Extract to a named constant:
```typescript
/** Max days a row's transactionDate can precede its periodStart index key. */
const EXTERNAL_LOOKBACK_MS = 31 * 86400000;
const scanFrom = args.fromTs - EXTERNAL_LOOKBACK_MS;
```

Downgrading to Info.

### WR-01: Quadratic label membership check in `reduceByWeekdayRolling`

**File:** `convex/reports/unitEconomics.ts:765-766`
**Issue:** `labels.includes(k)` inside loops over `orderCountByDay.keys()` and `unitCountByDay.keys()` is O(N²) where N = distinct order days. On large windows with sparse external revenue this is a correctness-adjacent quality issue — it does not produce wrong results but degrades server query time.
**Fix:**
```typescript
const labelSet = new Set(labels);
for (const k of orderCountByDay.keys()) if (!labelSet.has(k)) { labels.push(k); labelSet.add(k); }
for (const k of unitCountByDay.keys()) if (!labelSet.has(k)) { labels.push(k); labelSet.add(k); }
```

### WR-02: `SkuParetoChart` recomputes cumulative % over sliced rows — Pareto line semantics broken when slice < full list

**File:** `src/hooks/convex/useAnalytics.ts:59-60` and `src/components/analytics/SkuParetoChart.tsx:35-47`
**Issue:** `useSkuPareto(topN)` returns `skuTop.rows.slice(0, topN)`. `SkuParetoChart` recomputes `totalRevenue` from that slice and derives `cumulativePct` relative to the slice total. This means the Pareto line reaches 100% at the last visible bar regardless of how much revenue the unseen products represent. A user looking at "Top 10" products will see a Pareto curve that reaches 100% at product #10, even if those 10 products only represent 60% of actual revenue. This misrepresents the Pareto analysis.

The snapshot already computed correct `cumulativePct` (relative to full window revenue). The client should use those values.

**Fix:**
```typescript
// SkuParetoChart: remove totalRevenue recompute, use server cumulativePct directly
const withCumulative = data.map((d: { name: string; revenue: number; cumulativePct: number }) => ({
  ...d,
  displayName: truncateWithTooltip(d.name, 22).display,
  fullName: d.name,
  // use server-computed cumulativePct as-is
}));
```
Also remove the `running` accumulation block (lines 39-48 in SkuParetoChart.tsx).

### WR-03: `reduceTypeMixOverTime` returns `series: []` in the empty-orders case — inconsistent shape with populated-state response

**File:** `convex/reports/unitEconomics.ts:895-899`
**Issue:** When `current.orders.length === 0`, `reduceTypeMixOverTime` returns `{ buckets: [], series: [] }`. But when orders exist and are mapped through `reduceVolumeByType`, the returned `series` is `pre.typeCodes.map(code => ({ code, name, values: [] }))` — non-empty even when no items match any type. This shape inconsistency can cause downstream consumers to conditionally render zero bars (from empty series) vs. render bars with zero height (from populated series with zero values), depending on whether the empty-orders fast-path fires. The `TypeMixOverTime.tsx` `data.series.map(...)` call is robust to both, but legend rendering differs.
**Fix:**
```typescript
export function reduceTypeMixOverTime(
  current: WindowData,
  pre: Precomputed,
  granularity: "day" | "week",
) {
  // Delegate entirely — reduceVolumeByType handles empty WindowData gracefully.
  return reduceVolumeByType(current, pre, granularity);
}
```

### WR-04: `useSkuChannelMatrix` hook slices both `products` and `matrix` but not `channels` — channel list is unrestricted

**File:** `src/hooks/convex/useAnalytics.ts:61-66`
**Issue:**
```typescript
return { products: products.slice(0, topN), channels, matrix: matrix.slice(0, topN) };
```
`channels` is returned unsliced — it contains ALL channels present in the full snapshot (up to 20 products × all channels). This is cosmetically fine since channels are already sorted by revenue and the channel list is typically small, but a consumer that correlates `channels` with `matrix[i].channels` may get misaligned indices if the matrix row includes channels not present in the top-N slice. Currently `SkuChannelHeatmap.tsx` uses `row.channels` per-matrix-row directly (not the top-level `channels` array for indexing), so this is not currently broken. It is a latent bug waiting for a future consumer.
**Fix:** Document the asymmetry in a comment, or also slice channels by presence in the top-N matrix rows:
```typescript
// channels is not sliced — it reflects all channels in the full snapshot,
// not only those present in the top-N matrix rows. Consumers MUST use
// row.channels per-row, not the top-level channels for index alignment.
```

### IN-03: `DayHourHeatmap` `collapseOvernight` parses label strings via `split("-").map(Number)` — fragile string parsing

**File:** `src/components/analytics/DayHourHeatmap.tsx:20-24`
**Issue:** Hour-bin labels are parsed via `const [start] = l.split("-").map(Number)`. If the backend ever changes the label format (e.g., "0h-3h", "00:00-03:00"), this silently produces `NaN`, causing all bins to be misclassified as `start >= 9` (since `NaN >= 9` is false) — all columns would end up in the "Overnight" bucket. The backend contract is currently stable (locked by test), but the parsing is fragile.
**Fix:** Add a guard:
```typescript
const start = Number(l.split("-")[0]);
if (isNaN(start)) continue; // skip malformed labels
```
