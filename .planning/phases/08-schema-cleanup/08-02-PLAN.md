  <action>
**1. orders/queries.ts -- Remove all 6 deprecated fallback code paths:**

The research identified fallback code at approximately these locations (line numbers may have shifted). Each location has a pattern like:
```typescript
// FALLBACK: Deprecated fields for historical orders (pre-BOM)
if (item.productionType === "original" && item.productionUnits) { ... }
```

Remove all such fallback blocks. After removal, the code should ONLY use `orderItemProduction` records for ball stats. If a historical order has no production records, those items simply contribute 0 balls (which is correct -- they were never tracked in the BOM system).

**Specific locations to clean (search for `productionType` and `productionUnits` in this file):**

a. `calculateBallStats` function (~line 430): Remove the fallback block that reads `item.productionType === "original"` / `"bite_sized"`. The BOM (orderItemProduction records) path above it is the only path needed. If no production records exist for an item, skip it (0 balls).

b. Kitchen stats query (~line 722-727): Remove the fallback that reads `item.productionType` and `item.productionUnits` for calculating needed balls. Only use production records.

c. Completed stats (~line 759-762): Same pattern -- remove deprecated fallback.

d. Individual order detail (~line 1116-1119): Same pattern -- remove deprecated fallback.

e. Debug query (~line 960-961): Remove `deprecated_productionType` and `deprecated_productionUnits` from the debug output. These fields will no longer exist.

**For each removal:**
- Delete the entire fallback `if` block (including the "FALLBACK" comment)
- Keep the primary BOM/orderItemProduction code path
- If the BOM path has a `continue` before the fallback, the `continue` stays (it correctly skips items without production records)

**2. orders/mutations/packaging.ts -- Clean helper functions:**

a. `getBallsPerPackageForItem` (~line 23-39): Remove the fallback line `return item.productionUnits ?? 1;`. If no production records exist, return 1 as the default (same behavior, just not reading the deprecated field).

b. `hasProductionData` (~line 47-59): Remove the fallback `return !!item.productionType;`. If no active orderItemProduction records exist, return false.

**3. orders/whatsapp.ts -- Clean BOM fallback (~line 566):**

The line `const productionUnits = bomUnits ?? p.productionUnits ?? 1;` reads `p.productionUnits` as a fallback. Change to `const productionUnits = bomUnits ?? 1;` since BOM is the sole source. The `p.productionUnits` field will be removed from the schema.

**4. menuProducts/mutations.ts -- Two changes:**

a. **Replace isFixed deletion protection (~line 358):**
Change:
```typescript
if (product.isFixed) {
  throw new Error("Cannot delete fixed product. This is a core menu item.");
}
```
To:
```typescript
if (product.posSlot !== undefined || product.packagingPosSlot !== undefined) {
  throw new Error("Cannot delete a POS-assigned product. Remove the POS slot assignment first.");
}
```
Per research recommendation: protects any POS-assigned product from deletion, which is the practical intent of isFixed.

b. **Clean seed data (seedFixedProducts ~line 467-512):**
Remove `productionType`, `productionUnits`, and `isFixed` from all 4 fixed product definitions in the seed array. The seed should only set BOM-compatible fields: `code`, `name`, `grams`, `defaultPrice`, `unitCost`, `isActive`.

Also update the patch in the existing-product update path (~line 524-528) to remove `isFixed: product.isFixed`.

**Important:** Do NOT touch `convex/orders/mutations/migrations.ts` -- those migration functions intentionally read deprecated fields to create production records from historical data. They will continue to work since documents still have the data (clearing happens in Plan 03).
