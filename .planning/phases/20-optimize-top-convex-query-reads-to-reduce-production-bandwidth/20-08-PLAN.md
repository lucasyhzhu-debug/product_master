<objective>
Prune `getKitchenStats` intermediate data to reduce per-call payload from ~35 KB.

Purpose: `getKitchenStats` consumes 25 MB at 742 calls. The subscription MUST stay reactive (kitchen needs live updates). The optimization is purely payload reduction. The query currently fetches full `Doc<"orderItemProduction">` objects into maps but only uses numeric fields (`unitsRemaining`, `unitsCompleted`, `productionUnitCode`, `productionUnitTypeId`, `isCancelled`). The full Doc includes `orderId`, `orderItemId`, `productName`, `variant`, timestamps etc. that are never used in the aggregation.

However, the Convex DB query returns full documents — there's no projection. The key optimization: ensure the RESPONSE (return value) doesn't contain any full Doc objects. Currently the return is already aggregated numbers — verify this and optimize if any leakage exists.

Output: Verified/optimized query return shape.
</objective>

**Potential optimization: Reduce the number of status queries.**

Currently the query fetches 6 separate status groups (Draft, AwaitingPayment, PaymentReceived, BeingPrepared + Complete, AwaitingDelivery). For kitchen stats, we really only need:
- Pending: PaymentReceived + BeingPrepared (Draft and AwaitingPayment don't have production records yet)
- Completed today: Complete + AwaitingDelivery

Check if Draft and AwaitingPayment orders actually have `orderItemProduction` records. If not, skip fetching their items and production:

```typescript
// Only fetch orders that have production records
const [paymentReceivedOrders, beingPreparedOrders] = await Promise.all([
  ctx.db.query("orders").withIndex("by_status", (q) => q.eq("status", "PaymentReceived")).collect(),
  ctx.db.query("orders").withIndex("by_status", (q) => q.eq("status", "BeingPrepared")).collect(),
]);
const productionOrders = [...paymentReceivedOrders, ...beingPreparedOrders];

// Draft and AwaitingPayment included for count only, no item/production lookup needed
const [draftOrders, awaitingPaymentOrders] = await Promise.all([
  ctx.db.query("orders").withIndex("by_status", (q) => q.eq("status", "Draft")).collect(),
  ctx.db.query("orders").withIndex("by_status", (q) => q.eq("status", "AwaitingPayment")).collect(),
]);

const pendingOrders = [...draftOrders, ...awaitingPaymentOrders, ...productionOrders];
```

Then only fetch items/production for `productionOrders` (not all `pendingOrders`):

```typescript
// Only fetch items for orders that have production records
const relevantOrders = [...productionOrders, ...completedTodayOrders];
const relevantOrderIds = [...new Set(relevantOrders.map((o) => o._id))];
```

This reduces DB reads for Draft/AwaitingPayment orders (which don't have production yet). These orders are included in `pendingOrders.length` for the `ordersPending` count but skip the expensive item+production lookups.

BUT the CLAUDE.md workflow shows "PaymentReceived" not "Confirmed" — check if orders in PaymentReceived status DO have production records. If Draft and AwaitingPayment orders never have production records, this optimization is safe.

If unsure, keep the current approach but add a comment documenting why all 4 statuses are included.
