# Phase 59.1: Company Payment Request Flow - Context

**Gathered:** 2026-03-16
**Status:** Ready for planning

<domain>
## Phase Boundary

Add a 3rd payment type `payment_request` to the expense system for **prospective** company payments — where an employee requests the company to pay a vendor directly from the company bank account. Unlike `company_paid` (retrospective, money already left) and `employee_paid` (employee fronted money), this flow requires approval BEFORE money moves. After approval, someone executes the bank transfer and marks the expense as paid with a transaction reference.

Depends on Phase 59 (which establishes the 2-literal `employee_paid`/`company_paid` model and the `recorded` status).

</domain>

<decisions>
## Implementation Decisions

### Payment Method
- Add 3rd literal to `paymentMethod` union: `payment_request`
- Phase 59 establishes `employee_paid` and `company_paid` — this phase extends to 3 literals
- Frontend dropdown becomes 3 options: "Reimburse Employee", "Paid by Company", "Payment Request"

### How It Differs from the Other Flows
- `employee_paid` (retrospective): employee already paid → submit → admin approves → JE created → reimbursement
- `company_paid` (retrospective): company bank already debited → submit → JE auto-created → admin acknowledges
- `payment_request` (prospective): money hasn't moved yet → submit → admin approves → someone executes bank transfer → mark as paid → JE created

### Status Flow
- `draft` → `submitted` → admin approves → `approved` (no JE yet — money hasn't moved)
- After bank transfer executed: someone marks it as paid → status `paid` (new status) → JE created at this point (DR Expense, CR 1100 Cash/Bank)
- The "mark as paid" step captures `transactionReference` (bank ref number) and `paidAt` timestamp
- Admin can reject the request (standard reject flow) — no money moves, no JE

### Journal Entry Treatment
- Same JE as other flows: DR Expense Account (user-selected GL code), CR 1100 (Cash/Bank)
- JE created ONLY when marked as paid (not on submission, not on approval) — because money hasn't left the bank until then
- JE description: "Expense EXP-0316-001 [Payment Request]: Vendor payment for X"

### Approval Flow
- Standard approval flow — same as `employee_paid` (admin must explicitly approve)
- Admin approves = authorization to make the bank transfer, NOT confirmation that payment happened
- After approval, expense sits in `approved` status until someone marks it as paid
- Admin can approve it "straight away" per user's intent — but the approval gate exists for control

### Mark as Paid Step
- New mutation: `markAsPaid` — transitions `approved` → `paid`, creates JE, captures transaction reference
- Who can mark as paid: manager, admin (same roles that can approve)
- Required fields: `transactionReference` (mandatory — must have bank proof), `paidAt` (defaults to now)
- This is the step where the JE gets created

### Receipt / Evidence
- Receipt required on submission (same as `company_paid` — always required since it's company money)
- `transactionReference` captured at the "mark as paid" step (not at submission — bank transfer hasn't happened yet)

### Approval Queue Integration
- Payment requests appear in same approval list as other expenses
- Distinguished with a "Payment Request" badge (different from "Company Paid" badge)
- Standard Approve/Reject actions (same as employee_paid)
- After approval: expense moves to a "Pending Payment" state visible somewhere (approval queue or separate view)

### Claude's Discretion
- Whether "Pending Payment" (approved but not yet paid) expenses get their own tab/filter or just appear in the main list
- Exact UI for the "Mark as Paid" action (inline button, dialog, separate page)
- Whether `paidAt` should default to now or require manual entry
- Badge color for "Payment Request" vs "Company Paid" vs "Employee Paid"
- Whether to add a `paidBy` field tracking who executed the bank transfer

</decisions>

<specifics>
## Specific Ideas

- "There's a 3rd type of workflow where someone actively pays someone using the bank account — like we need to pay a vendor straight away, and we ask the manager to pay directly from our bank account to that vendor"
- "It still needs a flow for approval but an admin should just approve it straight away"
- The key distinction: this is the only prospective flow — money hasn't moved at submission time
- Transaction reference is captured AFTER payment execution, not at submission (unlike company_paid where it's captured at submission since the debit already happened)

</specifics>
