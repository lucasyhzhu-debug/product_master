1. `git revert <merge-commit>` — reverts all schema changes atomically

For pre-merge issues caught by tests: revert the specific schema edit and keep the field/table, noting it as "needs migration" in the audit report.

<task type="auto">
  <name>Task 2: Remove unused fields/tables, clean up over-indexes, apply trivial cleanups, update docs</name>
  <files>convex/schema.ts, docs/SCHEMA.md, docs/CHANGELOG.md</files>
  <action>
  Read `docs/SCHEMA_AUDIT.md` sections "Unused Tables/Fields", "Over-indexing", and "Quick-Win Candidates". Execute each safe quick-win:

  **A. Unused fields removal (Convex 2-step process):**
  For each field flagged as unused:
  1. **VERIFY via live query** — do NOT rely solely on the audit's code analysis. Run this in the Convex dashboard or as a one-off query in the dev environment:
     ```typescript
     ctx.db.query("tableName").filter(q => q.neq(q.field("fieldName"), undefined)).first()
     ```
     If this returns a document, the field HAS data and MUST NOT be removed as a quick-win.
  2. **If zero documents have the field AND no code writes to it:** Follow the Convex 2-step removal:
     - Step 1: If any documents exist with the field (even null/undefined), patch them to remove the field first
     - Step 2: Remove the field from the `v.object()` validator in `convex/schema.ts`
  3. If any query/mutation code references this field, remove those references too.
  4. **Edge case — field has data in 1-10 documents:** This is NOT a quick-win. It requires a data migration step. Flag in the audit report for future cleanup but do NOT remove the field in this phase.

  **B. Empty table removal:**
  For tables with zero documents AND fully superseded:
  1. Remove the `defineTable()` call from schema.ts.
  2. Remove any query/mutation files in the corresponding `convex/{tableName}/` directory.
  3. Remove any imports of the removed table's API endpoints.
  4. **Search `tests/` for test files referencing the dropped table or its API endpoints (`api.{tableName}.*`) and remove/update those tests.**

  **C. Over-index removal:**
  For indexes with zero `.withIndex()` references (confirmed against ALL backend files including `crons.ts` and `http.ts`):
  1. Remove the `.index()` definition from schema.ts.
  2. Verify no implicit usage: search for `.query('tableName').order()` calls without `.withIndex()` — these rely on Convex's default creation-time ordering, NOT custom indexes. Custom index removal is generally safe if no `.withIndex()` references exist.

  **D. Trivial denormalization cleanup:**
  For denormalized fields flagged as trivially removable (confirmed no-migration-required — field never written after a specific date, or field value can be recomputed from source data at runtime):
  1. Follow the same 2-step Convex process as section A.
  2. Remove any code that writes to this field in mutations.

  **E. Annotation updates:**
  - Ensure `productionCounts` table has a clear `// ARCHIVED: Read-only, superseded by productionLog aggregation` comment.
  - Ensure deprecated `productionType`/`productionUnits` fields have clear deprecation comments (keep fields, just annotate).

  **F. Documentation updates:**
  - Update `docs/SCHEMA.md` to reflect any dropped tables, removed fields, or added indexes.
  - Update `docs/CHANGELOG.md` with a summary of the schema audit findings and quick-win cleanups applied.

  **IMPORTANT constraints from CONTEXT.md:**
  - DO NOT drop `productionCounts` table (keep annotated as archived)
  - DO NOT remove `productionType`/`productionUnits` deprecated fields from `menuProducts` or `orderItems`
  - DO NOT execute complex denormalization cleanups that need data migration
  - For the `feedback` table: it is ACTIVELY USED (Layout.tsx, feedback components, hooks) — audit for stale fields only, do NOT recommend removal
  - **Before removing ANY field, table, or index:** also check `convex/crons.ts` and `convex/http.ts` for references — these runtime code paths are NOT covered by unit tests

  After all changes, run:
  1. `npm run build` — must pass
  2. `npm run test` — all existing tests must pass
  3. `npm run deploy:check` — pre-deploy dry run validation

  If any test fails due to a schema change, either:
  - Fix the test if it references a removed field/table (update test to not use removed artifact)
  - Revert the schema change if the test reveals the field/table IS actually used
