  <action>
  **Step 0: Archive existing audit report.**
  The file `docs/SCHEMA_AUDIT.md` (556 lines) already exists from the v1.0 Phase 8 audit (2026-02-14). Archive it:
  ```bash
  cp docs/SCHEMA_AUDIT.md docs/SCHEMA_AUDIT_2026-02-14.md
  ```
  Then overwrite `docs/SCHEMA_AUDIT.md` with the new 11-section format report below.

  **Step 1: Before starting, read `docs/SCHEMA.md` for documented design rationale on major tables.** This prevents flagging intentional design decisions as findings.

  **Step 2: Verify table count.** Run `grep -c "defineTable" convex/schema.ts` to get the authoritative table count (currently 65). Audit ALL tables — do not rely on the "59" figure from older docs.

  **Step 3: Read `convex/schema.ts` end-to-end** (1,600 LOC, 65 tables, 166 indexes). For EVERY table, perform these checks:

  **A. Unused tables/fields:**
  - For each table, grep all `convex/` files (excluding `_generated/`) for references to the table name in queries, mutations, helpers, **`crons.ts`, and `http.ts`** (these runtime code paths are NOT covered by unit tests and must be explicitly included).
  - A table with zero references (only schema definition) is "unused" — candidate for removal.
  - For each field in a table, check if it's referenced in any query return, mutation insert/patch, or filter. Fields never referenced in code are "potentially unused."
  - Special attention to known legacy items: `productionCounts` (archived — keep annotated, do NOT recommend removal), `feedback` (**ACTIVE — used in Layout.tsx, feedback components, and hooks — do NOT treat as removed**), deprecated `productionType`/`productionUnits` on `menuProducts` and `orderItems` (keep, just annotate).

  **B. Duplicate data across tables:**
  - Identify fields that store the same data in multiple tables (e.g., product name stored in both `orderItems` and `products`).
  - For each duplication, determine if it's intentional denormalization (check Phase 8 inline comments — ~56 annotations) or accidental drift.
  - Verify all Phase 8 denormalization annotations are still accurate against current query patterns — some may be stale after 6 milestones.

  **C. Missing indexes:**
  - For every `.withIndex("indexName", ...)` call across all query/mutation files **plus `crons.ts` and `http.ts`**, verify a matching `.index("indexName", ...)` exists in schema.ts.
  - Also verify there are no `.withIndex()` calls referencing index names that do NOT exist in schema.ts — these would be broken references (Critical severity).
  - For every `.query("tableName").filter(...)` call that does NOT use `.withIndex()`, check if an index SHOULD exist (high-frequency queries benefit from indexes).
  - For every `.query("tableName").order("desc")` or `.order("asc")` call, check if the sort field is indexed.

  **D. Over-indexing:**
  - For every `.index()` definition in schema.ts, grep all backend files **including `crons.ts` and `http.ts`** for `.withIndex("thatIndexName")`.
  - Indexes with zero `.withIndex()` references are candidates for removal (unless they serve implicit ordering).
  - Note: Convex indexes have storage cost and slow writes — unused indexes should be removed.

  **E. Denormalization waste:**
  - Identify denormalized fields that are never read without also reading the source table (pointless denormalization).
  - Identify denormalized fields that have drifted out of sync with their source (no update propagation code).

  **F. Cross-table relationship integrity:**
  - For every `v.id("otherTable")` foreign key reference, verify the referenced table exists and the relationship makes sense.
  - Check if `convex/integrityChecks/` already covers this relationship — note gaps.
  - Identify potential orphan risks: tables with foreign keys but no cascade/cleanup on source deletion.

  **G. Table merge candidates:**
  - Identify tables that store overlapping data and could potentially be merged.
  - Document rationale but do NOT recommend execution in this phase (per CONTEXT.md decision).

  **H. Index range bounds anti-pattern:**
  - Search for `.withIndex(...).filter(q => q.lt/lte/gt/gte(...))` patterns where the filter is applying a second range bound on the same indexed field.
  - These should use `.withIndex("idx", q => q.gte(start).lt(end))` instead of splitting bounds between `.withIndex()` and `.filter()`.
  - Known instances exist in `convex/externalData/queries.ts` (Phase 32 code review finding).
  - Note: `.filter()` on a DIFFERENT field than the index is normal and not an anti-pattern.

  **Severity classification for each finding:**
  - **Critical**: Causes incorrect query results, data loss risk, or significant performance degradation
  - **Moderate**: Unnecessary storage cost, maintenance burden, or suboptimal query patterns
  - **Low**: Minor cleanup opportunity, cosmetic, or very low impact

  **Report structure** (per CONTEXT.md — categorize by issue type, not domain):
  1. Summary Scorecard (total findings, severity breakdown per category, estimated effort)
  2. Duplicate Data findings
  3. Unused Tables/Fields findings
  4. Missing Indexes findings
  5. Denormalization Waste findings
  6. Over-indexing findings
  7. Cross-table Integrity findings
  8. Table Merge Candidates
  9. Index Range Bounds Anti-patterns
  10. Phase 8 Annotation Freshness Review
  11. Quick-Win Candidates (inputs for Plan 02)

  Each finding MUST include:
  - Table(s) affected
  - Severity (critical/moderate/low)
  - Description of the issue
  - Concrete remediation code snippet (exact field/table/index changes)
  - Whether it's safe as a quick-win (no data migration) or requires careful migration

  **IMPORTANT:** This is a 1,600 LOC schema with ~95 backend files containing `.withIndex()` calls. Work systematically — build a complete index cross-reference table (index name -> all files that use it) as an intermediate step before writing sections C and D. Read schema.ts in sections, grep query patterns in batches.
