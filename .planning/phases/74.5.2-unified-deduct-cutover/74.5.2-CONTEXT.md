**Cutover mechanics:**

- **D74.5.2-L4 — Backfill runs BEFORE flag flip for each channel.** For every channel except GoFood, the sequence per channel is: (a) backfill historical `externalRevenueItems` with `inventoryDeductedAt IS NULL`, (b) run per-channel audit, (c) resolve/dismiss audit issues, (d) flip flag, (e) soak 24–48h. This ensures all historical sales have deducted inventory before the go-forward flag flip — otherwise the first live sale would be the ONLY deducted sale for that channel, creating an inventory discontinuity.
  - **Why:** If flag flips first, live deductions start but historical gaps remain. Backfill-first establishes the baseline; flip goes forward cleanly.
  - **How to apply:** Runbook step order documented in `docs/CHANNEL_INTEGRATION.md`; admin UI progress cards reflect this sequence (backfill complete indicator gates flag-flip affordance — informational, not enforced; admin may still override).

- **D74.5.2-L5 — GoFood cutover is atomic (flip + retire in same merge).** Per parent D-14, `processGofoodSales` retirement happens atomically when the GoFood flag flips ON.   - **Why:** Both paths running concurrently would double-deduct inventory. Atomic flip-and-retire is the only safe sequence. But code-first + admin-triggered flag flip creates a small under-deduction window — acceptable (recoverable via backfill) vs double-deduction (only recoverable via manual row deletion).
  - **How to apply:** One plan covers `processGofoodSales` removal (function body + both gobiz adapter call sites) + runbook instruction to flip immediately post-deploy. Data migration (`gofood_sale → channel_sale + source: "gobiz"`) is a SEPARATE plan that runs AFTER the atomic retirement plan lands and soaks, so the migration rewrites only historical rows (no live writes to `"gofood_sale"` after the retirement plan deploys).

- **D74.5.2-L6 — Transaction literal migration is forward-only.** The `productInventoryTransactions` type migration writes `transactionType: "channel_sale" + source: "gobiz"` for rows currently `transactionType: "gofood_sale"`; `externalRef` derived from `gofoodOrderRef` (or `legacy-${_id}` fallback if null). **New structural decisions (added post-research):**

- **D74.5.2-L12 — Add compound index `by_source_deductedAt: ["source", "inventoryDeductedAt"]` on `externalRevenueItems`.** The existing index set (`by_revenue`, `by_source`, `by_menu_product`, `by_product_name`, `by_source_external_item`) does NOT support the backfill query `WHERE source = X AND inventoryDeductedAt IS NULL` efficiently — only `by_source` would match, requiring a post-scan filter over potentially millions of rows per source. Adding `by_source_deductedAt` lets backfill paginate with `.withIndex(..., q => q.eq("source", source).eq("inventoryDeductedAt", undefined)).take(200)` in constant time per page.
  - **Why:** Post-scan filter over `by_source` is O(N) per pagination page forever, pathological for 10K+ rows.
  - **How to apply:** Wave 1 schema change. One-line add to `externalRevenueItems` index list. Convex rebuilds on deploy. Cost: one additional index maintenance per insert (5 → 6 indexes); benefit compounds across 6 backfill runs.

- **D74.5.2-L13 — Backfill ignores flag state.** The `channelDeductionEnabled` flag gates ONLY the live `saveRevenueItems` dispatch path. Backfill actions call `processChannelSaleInternal` directly (not via `saveRevenueItems`), so the flag has no effect on backfill execution. This is intentional — admin-triggered backfill is a one-shot data-repair operation, separate from live-sync gating. Admin can run backfill with flag OFF, then flip flag ON when ready.
  - **Why:** If backfill honored flag-OFF, admin couldn't prepare historical data before flipping — breaking D74.5.2-L4 "backfill-before-flip" sequence.
  - **How to apply:** Runbook documents this behavior. Backfill UI does NOT display a flag-state warning. `processChannelSaleInternal` does not read the flag (already true in 74.5.1 impl per research).

- **D74.5.2-L14 — K3Mart cutover flips BOTH `k3mart` and `consignment` flags in one admin action.** Per parent D-12, K3Mart sync + consignment move together. Since `channelDeductionEnabled` has separate keys for `k3mart` and `consignment`, the admin UI ships a "K3Mart bundle" affordance (single button or clear UI copy that BOTH toggles must flip). Separate keys retained for fine-grained rollback.
  - **Why:** Admin ergonomics + reduces risk of forgetting one flag. Fine-grained rollback still available if one path misbehaves.
  - **How to apply:** `ProductInventorySettings.tsx` adds a "Flip K3Mart (both paths)" composite action. Underlying mutation `setChannelDeductionFlag` is invoked twice.

- **D74.5.2-L15 — GrabFood bucket stays permanent-OFF in 74.5.2.** OAuth `orders:read` scope is not granted; infrastructure works but returns 401. Per 74.5.1 CONTEXT D74.5.1-L5, GrabFood is `grabfood: false` forever-until-scope-granted. 74.5.2 ships the GrabFood backfill button (for future when scope arrives) but the button has no data to process today (zero GrabFood revenue items ingested).
  - **Why:** Don't block 74.5.2 on an external vendor gate.
  - **How to apply:** Ship the code path; the admin simply doesn't click it today.
