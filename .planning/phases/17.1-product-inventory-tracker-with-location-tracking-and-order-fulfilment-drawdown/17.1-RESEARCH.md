# Phase 17.1: Product Inventory Tracker with Location Tracking and Order Fulfilment Drawdown - Research

**Researched:** 2026-02-20
**Domain:** Finished goods inventory management (Convex backend + React frontend)
**Confidence:** HIGH

## Summary

This phase adds a **finished goods inventory layer** for sellable products (boxed menu products). It is architecturally distinct from the existing packaging inventory (FIFO batches of boxes/stickers) and ingredient inventory (Phase 20). The core data model is simple: a `productInventory` table tracking stock per `menuProduct` per location, with a `productInventoryTransactions` audit log. Two consumption paths exist: (1) manual "Use Available Inventory" button on order detail that draws down stock and advances the order, skipping kitchen production; (2) automatic deduction during GoBiz sync (Phase C in `convex/integrations/gobiz/adapter.ts`).

The existing codebase provides strong patterns to follow. The `componentStock` / `componentTransactions` / `inventoryBatches` system (packaging inventory) and `gofoodDepotStock` (GoFood depot tracking) are both directly relevant. The `storageLocations` table can be extended with new location types for this feature. The InventoryManager page already has category filtering (`production` | `packaging`) and can accommodate a new "Finished Goods" tab.

**Primary recommendation:** Create a new `productInventory` table (not reuse componentStock which is FIFO-batch-oriented) and a `productInventoryTransactions` audit log. Extend `storageLocations` with a `"depot"` location type for GoFood outlets. Add a `productInventorySettings` single-row table for configurable thresholds. Hook into the existing GoBiz sync Phase C for automatic GoFood deductions. Add "Use Available Inventory" button to OrderDetail when status = PaymentReceived.

## Architecture Patterns

### Recommended Schema Additions

```
convex/schema.ts additions:

productInventory: defineTable({
  menuProductId: Id<"menuProducts">,
  locationId: Id<"storageLocations">,
  quantity: number,           // Current stock (can go negative for GoFood)
  lowStockThreshold: optional(number),  // Per-product-location override (null = use global)
  lastUpdated: number,
})
  .index("by_menu_product", ["menuProductId"])
  .index("by_location", ["locationId"])
  .index("by_product_location", ["menuProductId", "locationId"])

productInventoryTransactions: defineTable({
  menuProductId: Id<"menuProducts">,
  locationId: Id<"storageLocations">,
  transactionType: union(
    "add",           // Kitchen adds stock
    "drawdown",      // Order fulfilment drawdown
    "gofood_sale",   // GoFood sync auto-deduction
    "adjust",        // Manager adjustment (spoilage, correction, transfer)
  ),
  quantity: number,           // + for add, - for drawdown
  previousQuantity: number,   // Stock before this transaction
  newQuantity: number,        // Stock after this transaction
  orderId: optional(Id<"orders">),
  gofoodOrderRef: optional(string),  // GoFood order reference
  reason: optional(string),          // For adjustments
  performedBy: string,
  createdAt: number,
})
  .index("by_product_location", ["menuProductId", "locationId", "createdAt"])
  .index("by_location", ["locationId", "createdAt"])
  .index("by_order", ["orderId"])
  .index("by_type", ["transactionType", "createdAt"])

productInventorySettings: defineTable({
  globalLowStockThreshold: number,    // Default 5
  defaultAddLocation: optional(Id<"storageLocations">),
  autoAdvanceOnDrawdown: boolean,     // Default true
  alertMode: union("toast", "toast_and_badge"),
  updatedBy: string,
  updatedAt: number,
})

// Extend storageLocations.locationType union:
locationType: union("office", "kitchen", "venue", "depot")
```

### Pattern 1: Simple Stock Model (Not FIFO)
**What:** Unlike packaging inventory which tracks individual batches with supplier/cost data, finished goods use a simple aggregate: one row per product per location with a single quantity field.
**When to use:** Finished goods are fungible — a box of Original Single is a box of Original Single regardless of when it was packed. No purchase cost tracking needed (COGS comes from BOM).
**Why:** The FIFO batch model (`inventoryBatches` + `componentStock`) is overkill for finished goods. It would add complexity without value.

### Pattern 2: Order Drawdown as Mutation
**What:** A single mutation that validates stock availability across all order items, deducts stock, logs transactions, and advances order status. Atomic — all-or-nothing.
**When to use:** When staff clicks "Use Available Inventory" on OrderDetail.
**Key behavior:**
- Validates every order item's menuProduct has sufficient stock at the chosen location
- Blocks on any shortfall (shows what's available vs needed)
- On success: deducts stock, creates transaction records, advances order to AwaitingDelivery
- Skips kitchen production entirely (no orderItemProduction records, no ball tracking)

### Pattern 3: GoFood Sync Hook
**What:** Add a Phase D to the GoBiz sync flow (after existing Phase C sticker deduction) that deducts finished goods from the matching outlet's product inventory.
**When to use:** Automatic on every GoBiz sync (manual or cron).
**Integration point:** `convex/integrations/gobiz/adapter.ts` — both `syncGoBizRevenue` and `autoSyncGoBizRevenue` have Phase C blocks. Add Phase D after Phase C.
**Key behavior:**
- Uses the same `allNewRecords` with `linkedMenuProductId` data
- Maps merchantId -> externalOutletId -> storageLocationId (new linkage needed)
- Allows negative stock (GoFood sales must never be blocked)
- Logs transaction with GoFood order reference

### Pattern 4: InventoryManager Tab Integration
**What:** Add a "Finished Goods" tab to the existing InventoryManager page alongside the current Packaging and Ingredients views.
**When to use:** Always — this is the primary entry point.
**Implementation:** The InventoryManager already has `categoryFilter` state and a `Tabs` component. Add a new tab that renders a dedicated FinishedGoodsTab component showing:
- Product cards with stock per location
- Quick add-stock form
- Low-stock visual indicators
- Transaction history per product

### Anti-Patterns to Avoid
- **Don't reuse componentStock for finished goods:** Different data model (no batches, no FIFO, no supplier tracking). Would confuse existing inventory queries.
- **Don't modify existing order status transitions for drawdown:** The drawdown is a separate action that happens to advance status. Don't embed it in `moveForward` — keep it as a separate mutation.
- **Don't create finished goods from kitchen production automatically:** The user explicitly decided kitchen adds stock manually via the Finished Goods tab. Auto-creation from production log would create ghost inventory.

## Common Pitfalls

### Pitfall 1: Race Conditions in Stock Deduction
**What goes wrong:** Two users simultaneously try to draw down from the same location, both see sufficient stock, both proceed, stock goes negative.
**Why it happens:** Convex mutations are serialized per-document, but the read-then-write pattern across multiple documents (productInventory + orders) can race.
**How to avoid:** Convex handles this — mutations are transactional. The read-then-write within a single mutation is atomic. However, optimistic concurrency means the mutation may retry. Ensure the mutation is idempotent.
**Warning signs:** Stock going negative for direct orders (should only be allowed for GoFood).

### Pitfall 2: storageLocations locationType Schema Migration
**What goes wrong:** Adding `"depot"` to the `locationType` union in schema.ts requires all existing code that validates location types to handle the new value.
**Why it happens:** TypeScript will flag exhaustive switch statements, but runtime validators (e.g., in storageLocations/mutations.ts) explicitly list allowed values.
**How to avoid:** Update the `storageLocations.create` mutation to accept `"depot"`. Update the `storageLocations.update` mutation similarly. Check for any UI components that map locationType to display strings.
**Warning signs:** "Invalid location type" errors when seeding depot locations.

### Pitfall 3: GoFood Outlet-to-Location Mapping
**What goes wrong:** The GoBiz sync knows about `externalOutlets` (with merchantId), but productInventory uses `storageLocations`. Need a mapping between them.
**Why it happens:** GoFood outlets (Crystal G347061572, Goldfinch G293156297, Tamtem G958262444) are `externalOutlets` records. Storage locations are `storageLocations` records. They're different tables.
**How to avoid:** Either add a `storageLocationId` field to `externalOutlets`, or create a mapping table, or use a naming convention lookup. **Recommendation: Add `linkedStorageLocationId: v.optional(v.id("storageLocations"))` to `externalOutlets` table.** This keeps the mapping clean and queryable. Seed the linkage when seeding locations.
**Warning signs:** GoFood sync deductions not finding the right location.

### Pitfall 4: Order Status after Drawdown
**What goes wrong:** The CONTEXT.md says drawdown should advance to `WaitingShipment` or `WaitingPickup` based on delivery method. But the current schema uses Phase 14's simplified statuses: `AwaitingDelivery` replaces both.
**Why it happens:** CONTEXT.md was written before checking current status names. The simplified 7-status Kanban (Phase 14) merged WaitingShipment/WaitingPickup into `AwaitingDelivery`.
**How to avoid:** Drawdown should advance from `PaymentReceived` directly to `AwaitingDelivery` (skipping `BeingPrepared`). This is the "smart skip" — kitchen production is bypassed.
**Warning signs:** Orders stuck in `BeingPrepared` when they should have skipped to `AwaitingDelivery`.

### Pitfall 5: InventoryManager Category Filter Interaction
**What goes wrong:** The existing InventoryManager uses `componentTypes` with `category: "production" | "packaging"`. Finished goods are `menuProducts`, not `componentTypes`. The existing category filter won't apply.
**Why it happens:** Finished goods are a fundamentally different entity than component types.
**How to avoid:** The Finished Goods tab should be a completely separate tab with its own data source (`productInventory` + `menuProducts`), not filtered through the existing componentTypes query. Think of it as a parallel view, not a filter.
**Warning signs:** Empty finished goods tab, or finished goods mixed into packaging/ingredients views.

### Pitfall 6: Existing gofoodDepotStock Duplication
**What goes wrong:** The `gofoodDepotStock` table already tracks per-product stock at the GoFood depot. Adding `productInventory` for the same products at the same locations creates dual sources of truth.
**Why it happens:** `gofoodDepotStock` was purpose-built for GoFood depot tracking (Phase 13). The new `productInventory` is a broader finished-goods system.
**How to avoid:** **Migrate gofoodDepotStock into productInventory for depot locations.** Or: keep both but make productInventory the source of truth and update gofoodDepotStock from it. **Recommendation: Keep gofoodDepotStock for now (it has stickerDeficit tracking which is GoFood-specific). Have Phase D of GoBiz sync write to BOTH `productInventory` and `gofoodDepotStock`.** Later consolidation phase can merge them.
**Warning signs:** Stock numbers diverging between the two tables.

### Add Stock Mutation Pattern
```typescript
// convex/productInventory/mutations.ts
export const addStock = mutation({
  args: {
    token: v.string(),
    menuProductId: v.id("menuProducts"),
    locationId: v.id("storageLocations"),
    quantity: v.number(),
  },
  handler: async (ctx, args) => {
    const user = await requireRole(ctx, args.token, ["kitchen", "order_staff", "manager", "admin"]);

    const existing = await ctx.db
      .query("productInventory")
      .withIndex("by_product_location", (q) =>
        q.eq("menuProductId", args.menuProductId).eq("locationId", args.locationId)
      )
      .first();

    const previousQty = existing?.quantity ?? 0;
    const newQty = previousQty + args.quantity;

    if (existing) {
      await ctx.db.patch(existing._id, { quantity: newQty, lastUpdated: Date.now() });
    } else {
      await ctx.db.insert("productInventory", {
        menuProductId: args.menuProductId,
        locationId: args.locationId,
        quantity: newQty,
        lastUpdated: Date.now(),
      });
    }

    // Audit log
    await ctx.db.insert("productInventoryTransactions", {
      menuProductId: args.menuProductId,
      locationId: args.locationId,
      transactionType: "add",
      quantity: args.quantity,
      previousQuantity: previousQty,
      newQuantity: newQty,
      performedBy: user.name,
      createdAt: Date.now(),
    });

    return { newQuantity: newQty };
  },
});
```

### Order Drawdown Mutation Pattern
```typescript
// convex/productInventory/mutations.ts
export const fulfillFromInventory = mutation({
  args: {
    token: v.string(),
    orderId: v.id("orders"),
    locationId: v.id("storageLocations"),
  },
  handler: async (ctx, args) => {
    const user = await requireRole(ctx, args.token, ["order_staff", "manager", "admin"]);

    const order = await ctx.db.get(args.orderId);
    if (!order || order.status !== "PaymentReceived") {
      throw new Error("Order must be in PaymentReceived status");
    }

    // Get all order items
    const orderItems = await ctx.db
      .query("orderItems")
      .withIndex("by_order", (q) => q.eq("orderId", args.orderId))
      .filter((q) => q.neq(q.field("isCancelled"), true))
      .collect();

    // Check availability for ALL items first
    const shortages = [];
    for (const item of orderItems) {
      if (!item.menuProductId) continue;
      const stock = await ctx.db
        .query("productInventory")
        .withIndex("by_product_location", (q) =>
          q.eq("menuProductId", item.menuProductId!).eq("locationId", args.locationId)
        )
        .first();

      const available = stock?.quantity ?? 0;
      if (available < item.quantity) {
        shortages.push({
          productName: item.productName,
          needed: item.quantity,
          available,
        });
      }
    }

    if (shortages.length > 0) {
      throw new ConvexError({ type: "insufficient_stock", shortages });
    }

    // Deduct all items atomically
    for (const item of orderItems) {
      if (!item.menuProductId) continue;
      // ... deduct and log (similar to addStock but negative)
    }

    // Advance order status to AwaitingDelivery (skip BeingPrepared)
    await ctx.db.patch(args.orderId, {
      status: "AwaitingDelivery",
      isKitchenVisible: false,
    });

    // Log status transition
    await logStatusTransition(ctx, args.orderId, "PaymentReceived", "AwaitingDelivery",
      "Fulfilled from inventory (skipped production)", "user", user._id);
  },
});
```

## Open Questions

1. **Packaging Inventory Deduction on Drawdown**
   - What we know: When an order is fulfilled from inventory, the boxes are already packaged. The packaging materials were consumed when the boxes were originally made.
   - What's unclear: Should the drawdown mutation ALSO reserve/consume packaging inventory (boxes, stickers)? Or were those already consumed when the kitchen originally packed the product?
   - Recommendation: Do NOT deduct packaging inventory on drawdown. The boxes were already made and packaging was consumed at production time. Drawdown only deducts finished goods.

2. **Crystal Location Reuse**
   - What we know: The existing `storageLocations` has "Office" (default), "Kitchen", and "Legato Goldfinch". The CONTEXT.md says "Crystal = HQ / default".
   - What's unclear: Is "Crystal" the same as "Office"? Should we create a new "Crystal" location or alias the existing Office?
   - Recommendation: "Crystal" IS the Office/HQ location. Use the existing default location. Rename it in the UI if needed, or add "Crystal" as a display alias. Don't create a duplicate.

3. **GoFood Outlet-to-StorageLocation Seeding**
   - What we know: GoFood outlets exist in `externalOutlets`. Storage locations exist in `storageLocations`. Need a mapping.
   - What's unclear: Which GoFood outlets should have corresponding storage locations? All three (Crystal, Goldfinch, Tamtem)?
   - Recommendation: Create storage locations for Goldfinch (already exists as "venue") and Tamtem (new "depot" type). Crystal maps to the existing Office/default location. Add `linkedStorageLocationId` to `externalOutlets` for the mapping.
