<global_execution_rules>
<!-- Non-negotiable rules that apply to EVERY task in this plan. Violations are bugs. -->

**R1 — No per-item DB lookups (N+1 ban).**
`loadFilteredData` (introduced in Task 4) returns `{ orders, orderItems, orderById: Map<Id<"orders">, Doc<"orders">>, unitsPerProduct, unitsByTypePerProduct }`. Every query in Tasks 5–9 that needs an order for a given item MUST look it up via `orderById.get(it.orderId as string)` (or the correctly-typed key). NEVER call `ctx.db.get(it.orderId)` inside an orderItems loop. The map is pre-populated precisely to keep these queries at O(N) dispatch + O(1) lookup. `grep -E "ctx\.db\.get\(it\.orderId\)" convex/reports/unitEconomics.ts` MUST return 0 hits.

**R2 — Dedup is on the ORDER, not the ITEM.**
When the `by_order_date` fallback scan runs after the primary `by_completed_at` scan, it must skip any order whose `completedAt` is already defined (those orders were captured by the primary). The guard is `if (o.completedAt !== undefined) continue;` — never `if (it.completedAt !== undefined)` (orderItems do not have `completedAt`).

**R3 — Critical Rule §3: dynamic BOM iteration.**
No hardcoded `BIG_BALL`/`MID_BALL`/`HAZELNUT_REGULAR` in any unit-counting code path. Helpers iterate `componentTypes` where `category === "production" AND unit === "pcs"`. The only acceptable literal references to those codes are in test fixtures, migration strings, and the backward-compat shape (`bigBalls`/`midBalls` fields returned by dispatchPlanner for existing UI consumers).

**R4 — Revenue math via helpers only.**
Every revenue derivation uses `itemNetRevenue(it)` / `itemGrossRevenue(it)` / `itemDiscount(it)` from `convex/reports/revenueHelpers.ts`. `grep -E "it\.quantity \* it\.unitPrice" convex/reports/unitEconomics.ts` MUST return 0 hits.

**R5 — No cross-channel double-count (external vs internal ONLY).**
After Task 4b merges `externalRevenueItems` into the unified item stream, rows where `source === "internal"` must be skipped — `internal` is a projection adapter that mirrors every `orders` row into `externalRevenue`, so including both would double-count. **All other external sources (`gobiz`, `grabfood`, `k3mart`, `bigseller`, `shopee`, `tiktok`, `consignment`) do NOT have `orders` twins** and must be INCLUDED. Verified by grep: `ctx.db.insert("orders")` appears zero times in `convex/integrations/gobiz/`, `convex/integrations/bigseller/`, and `convex/integrations/grabfood/`. Skipping `gobiz` would zero out all GoFood revenue — the exact gap Task 4b closes. Tasks 5–9 downstream of 4b MUST iterate `unifiedItems` (not `orderItems`) for any cross-channel aggregation.

**R7 — Loader returns `unifiedItems` only, not `orderItems`.**
`loadFilteredData` return shape is `{ orders, unifiedItems, orderById, unitsPerProduct, unitsByTypePerProduct, unmatchedExternalItems }`. Do NOT also return the raw `orderItems` array — having both creates a copy-paste landmine where an executor iterates `orderItems` instead of `unifiedItems` and silently excludes external channels. Acceptance grep: `grep -E "orderItems:" convex/reports/unitEconomics.ts` on the return type must return 0 hits. If an executor needs internal-only orderItems for a debug path, filter `unifiedItems.filter(i => i._source === "internal")` at the call site.

**R6 — External items have no item-level discount data (Phase 80 scope only).**
As of Phase 79's output, `externalRevenueItems` captures `totalPrice` only — item-level discount is not ingested from marketplaces. For Task 4b's lifetime, external rows treat `lineTotal === totalPrice` and `discountAmount === 0`. The take-rate widget is scoped to "discount only, fees deferred" per CONTEXT.md D-C4; this is consistent. Do NOT fabricate per-item discounts by prorating parent `externalRevenue.commission`/`adBurn`/`promoBurn` — deferred to v2 contribution-margin lens. **Revisit this rule if** Phase 79 (or a later refactor) starts ingesting item-level discounts into `externalRevenueItems` — at that point, `revenueHelpers` will naturally read `discountAmount` via the `RevenueBearing` interface with no code change, and R6 should be retired.

These rules are enforced by acceptance-criteria greps on each task. If a task's acceptance criteria conflict with a rule, the rule wins — stop and flag before proceeding.
