# Phase 84 — UI Design Contract

> Visual and interaction contract for the QRIS payment frontend (Charge-via-QRIS button, `QrisChargeDialog`, `needsReview` badge). Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Scope note:** This phase ships exactly THREE UI surfaces, all on the existing order-detail page, all reusing existing primitives. No new design tokens, no new registry components, no new pages. The dialog state machine (active / paid / expired) is the only novel interaction. Everything else is contract reuse.

## Spacing Scale

Declared values (multiples of 4). Matches existing Tailwind spacing usage in order dialogs.

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-label gap (`gap-1`), badge inline padding |
| sm | 8px | Button/badge gaps (`gap-2`), tight stacks |
| md | 16px | Default dialog content stack (`space-y-4`), section padding |
| lg | 24px | Dialog section breaks, QR-block vertical margin |
| xl | 32px | (reserved — not expected this phase) |

Exceptions:
- **Touch targets:** primary action buttons use `min-h-[44px]` on mobile, `sm:min-h-[36px]` on desktop — matches `PaymentMethodButtons`. This is a POS phase (staff on phones/tablets at bazaars/counter), so the 44px mobile target is mandatory, not optional.
- **QR canvas:** `qrcode.react` rendered at a fixed scannable size of **256px** (square) on desktop, capped to viewport width minus dialog padding on mobile (`max-w-[256px] w-full aspect-square`). 256 is not on the 4-grid as a spacing token; it is a fixed component dimension, exempt.

## Typography

Inter only. Two weights in active use this phase: regular (400) and semibold (600). `font-medium` (500) is permitted for the existing dialog-label convention (`text-sm font-medium`) since it is the established label weight in `ConfirmationDialog.tsx`.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Display (amount) | 28px (`text-3xl` ≈ 30px acceptable) | 600 (semibold) | 1.2 — the IDR amount under/above the QR is the focal number |
| Heading (DialogTitle) | 20px (`text-lg`) | 600 (semibold) | 1.2 |
| Body / description | 16px (`text-base`) mobile, 14px (`text-sm`) desktop | 400 (regular) | 1.5 |
| Label / meta (NMID, countdown, merchant name) | 14px (`text-sm`) / 12px (`text-xs` for sub-labels) | 400 regular; 500 for inline labels | 1.5 |

Notes:
- **Countdown timer** renders at `text-sm`/`text-base`, regular weight, in `--color-status-warning` when ≤ 5 min remaining, otherwise `text-muted-foreground`.
- **Amount** is the largest type in the dialog — formatted as IDR (`Rp 1.500` style, dot thousands separator, no decimals) per existing app currency convention.

## Color

60/30/10 split inherits the app-wide theme tokens from `src/index.css` (`@theme`). This phase introduces NO new color tokens.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `--color-background` (light `hsl(0 0% 100%)` / dark `hsl(224 10% 10%)`) | Dialog body, page surface |
| Secondary (30%) | `--color-card` / `--color-muted` (`hsl(210 40% 96.1%)`) | Dialog panel, QR backdrop card, meta rows |
| Accent (10%) | `--color-primary` brand teal (`hsl(172 90% 30%)`) | See reserved list below |
| Destructive | `--color-destructive` (`hsl(0 84.2% 60.2%)`) | NOT used this phase — no destructive QRIS action exists (no void/cancel/refund — explicitly out of SPEC scope) |

Accent (teal `primary`) reserved for:
1. The **"Charge via QRIS"** trigger button (primary variant) on the order detail page.
2. The **"Regenerate"** button in the dialog's expired state (primary variant).
3. Focus rings on interactive dialog controls (`ring-primary`, existing convention).

Semantic status colors (existing tokens, NOT counted in the 10% accent budget — they are state signals, not brand accent):
- **Paid state:** `--color-status-success` (`#059669` / dark `#34D399`) + `--color-status-success-bg` for the success panel and the `CheckCircle2` icon. (Matches the green success convention already in `ConfirmationDialog`.)
- **Expired / countdown-low / `needsReview` badge:** `--color-status-warning` (`#D97706` / dark `#FBBF24`) + `--color-status-warning-bg`. The `needsReview` badge uses the **warning** palette (it is an attention indicator, not an error — payment WAS honored).
- **Webhook/load error inside dialog:** `--color-status-error` + `--color-status-error-bg`.

The QR code itself: black modules on white background (`qrcode.react` defaults). Do NOT tint QR modules with brand color — scannability and BI/QRIS contrast requirements take priority. White QR background is mandatory even in dark mode (wrap the QR in a fixed white card).

## Copywriting Contract

All copy in English (app default; matches existing order-detail UI).

| Element | Copy |
|---------|------|
| Primary CTA (trigger button) | **"Charge via QRIS"** (with `QrCode` lucide icon, leading) |
| Dialog title — active state | **"Scan to Pay with QRIS"** |
| Dialog title — paid state | **"Payment Received"** |
| Dialog title — expired state | **"QR Code Expired"** |
| Amount label | **"Amount due"** above the IDR figure |
| Countdown label | **"Expires in {mm:ss}"** (switches to warning color at ≤ 5:00) |
| NMID/merchant block (when `qrisNmid` set) | merchant name on line 1, **"NMID: {qrisNmid}"** on line 2, both `text-xs text-muted-foreground`, centered under QR (BI display convention) |
| Active-state helper body | **"Ask the customer to scan this code with any QRIS-enabled app. This screen updates automatically when payment is received."** |
| Paid state body | **"Rp {amount} received via {source}. The order has moved to Payment Received."** (`{source}` = paying wallet, e.g. DANA; omit the "via {source}" clause if `source` is absent) |
| Paid state — `needsReview` note | **"This payment needs review — {reviewReason}. The payment was still recorded."** rendered in a warning panel inside the paid state |
| Expired state body | **"This QR code is no longer valid. Generate a new one to charge the customer again."** |
| Regenerate CTA (expired state) | **"Generate New QR"** |
| Loading / generating state | **"Generating QR code…"** with a `Skeleton` placeholder sized to the 256px QR area |
| Dialog dismiss | **"Close"** (outline variant, `DialogFooter`) — present in all states; never the primary action |
| Error state (create action / webhook query fails) | heading **"Couldn't generate QR code"**, body **"Something went wrong reaching the payment provider. Close this and try again, or fall back to manual payment."**, plus a **"Try Again"** button |
| `needsReview` inline badge (order detail, D-02) | Badge text **"Needs review"**; on hover/focus a `Tooltip` shows the full `reviewReason` |
| Empty state | **Not applicable** — the dialog is only reachable for an `AwaitingPayment` order with an active payment context; there is no list/collection surface. The "no active QR yet" condition is the trigger button itself, not an empty state. |

Destructive actions: **NONE.** No void, cancel, refund, or delete in this phase (all explicitly out of SPEC scope). "Generate New QR" supersedes the prior pending row server-side but is non-destructive from the user's mental model (the old QR was already expired) — render it as a **primary** action, NOT a destructive/`AlertDialog` confirmation. No `window.confirm`/`window.prompt` (consistent with the no-`window.prompt`-in-admin-UI lesson from Phase 74.5.1).

## Interaction Contract (phase-specific)

The `QrisChargeDialog` is a single component driven by the `getActiveQrisPayment(orderId)` subscription (D-03). State is derived, not locally toggled:

| State | Trigger | Renders |
|-------|---------|---------|
| **loading** | action in flight / subscription resolving | Skeleton in QR slot + "Generating QR code…" |
| **active** | latest row `status === "pending"` and not past `expiresAt` | QR (256px, white card) + "Amount due" + amount + optional NMID/merchant block + "Expires in mm:ss" countdown |
| **paid** | row flips to `status === "paid"` (webhook-driven, reactive — NO manual refresh) | green success panel, `CheckCircle2`, paid body copy; if `needsReview` also a warning sub-panel |
| **expired** | row `status === "expired"` OR countdown reaches 0 | warning state + "Generate New QR" primary button |
| **error** | create action throws / subscription error | error panel + "Try Again" |

Visibility rule (button mount): the "Charge via QRIS" button renders **only** when `order.status === "AwaitingPayment"` AND the `QRIS_ENABLED` flag query returns true. Button is absent (not disabled) otherwise.

Reactivity: the paid flip is the headline UX guarantee — staff watch the screen, payment confirmation arrives via webhook, the dialog transitions without any click. The countdown is a local `setInterval` derived from `expiresAt`; it must clear on unmount.

Placement: trigger button mounts near the existing `PaymentMethodButtons` on the order detail page. The `needsReview` badge (D-02) mounts inline next to the order's payment status — minimal indicator only, NO list/filter/resolve flow (deferred to Phase 77).
