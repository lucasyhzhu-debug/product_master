**Section 1: Threat Model**
Frame the app's security context:
- Internal operations tool for ~5-15 staff at an Indonesian FMCG snack company
- Not exposed to public internet users; accessed by trusted kitchen/warehouse/office staff
- Primary risks: accidental data corruption, not external attacks
- Deployed on Convex (managed infrastructure) + Vercel (managed hosting) — platform handles network security, DDoS, TLS

**Section 2: Authentication Flow**
Use bullet-point flow (per Claude's discretion on narrative vs bullets):
1. Frontend shows active user list (no PIN hashes exposed via query filtering)
2. User selects avatar, enters 4-6 digit PIN
3. Backend verifies PIN with salted SHA-256, checks lockout status (5 attempts / 15-min cooldown)
4. On success: creates session with UUID v4 token, 8-hour expiry
5. Frontend stores session in localStorage (token, userId, name, role, expiresAt)
6. Protected mutations receive token in args, validated by requireRole()
7. requireRole() checks session table: token lookup via index, expiry check, role membership
8. ProtectedRoute handles client-side route guards by permission

**Section 3: Accepted Security Patterns**

Sub-section 3a: Environment Configuration
- Sensitive env files (.env, .env.local.production, .env.local.testing) removed from version control
- History scrubbed to remove past exposure (see Plan 02-02 for scrub details)
- Only .env.example template remains committed with placeholder values
- .gitignore updated to prevent future accidental commits

Sub-section 3b: Token-in-Args Authentication
- Convex functions are called over WebSocket (wss://), not HTTP — no request headers available
- Token passed as function argument serves same purpose as Authorization bearer header
- Transport is TLS-encrypted; token never travels in plaintext
- Convex built-in auth (ctx.auth) requires external providers (Clerk/Auth0) — overkill for internal PIN-based tool
- 39 mutations across 11 files use this pattern via requireRole() helper

Sub-section 3c: PIN Hashing (SHA-256 + Salt)
- Each PIN gets unique UUID salt (crypto.randomUUID()), preventing rainbow tables
- SHA-256 via Web Crypto API (crypto.subtle.digest) — not bcrypt/scrypt
- Acceptable because: PIN space is only 4-6 digits (max 1M combinations), rate-limited by 5-attempt lockout with 15-min cooldown, internal tool with no external access
- Convex runtime doesn't support native modules (bcrypt requires C bindings), so SHA-256 via Web Crypto is the strongest available option
- Reference: convex/lib/auth.ts:hashPin()

**Section 4: Known Limitations**
Honest list of consciously accepted trade-offs:
- **No constant-time PIN comparison**: verifyPin() uses === string comparison. Timing attacks are impractical over WebSocket transport with variable latency on an internal tool.
- **localStorage for session storage**: Tokens stored in localStorage, not httpOnly cookies. Acceptable because XSS risk is minimal on internal tool with no user-generated content.
- **Hardcoded K3Mart credentials**: convex/platformCredentials/mutations.ts contains default email/password for K3Mart integration. Should be moved to environment variables in a future phase.
- **No session cleanup cron**: Expired sessions accumulate until manual cleanup mutation is called. Low impact — sessions table is small.
- **Deployment identifier in frontend bundle**: VITE_CONVEX_URL embeds deployment name in client JS. This is by design (Convex requires it) and is semi-public information.

End the file with a "Last updated" date stamp.
