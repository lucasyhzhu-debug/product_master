## Decisions Made

- `processGofoodSales` takes `outletId` (not `merchantId`) as argument — avoids double lookup (outletId is already available in the revenue record's `outletId` field, merchantId->outlet resolution would be redundant)
- Phase D items aggregated by `(outletId::menuProductId)` composite key to correctly deduct per-outlet rather than cross-outlet aggregation
- `getRevenueById` added as `internalQuery` — action context in adapter requires `ctx.runQuery(internal....)` access to revenue record
- `fulfillFromInventory` bypasses `isValidForwardTransition()` and patches status directly — this is intentional, the map is 1:1 for happy-path, drawdown is a special exit path

### Design Decision: outletId vs merchantId for processGofoodSales

**Plan specified:** Pass `merchantId: v.string()` to `processGofoodSales` and look up outlet by `by_source_external_id` index.

**Actual implementation:** Pass `outletId: v.id("externalOutlets")` directly.

**Reason:** The GoBiz adapter already resolves merchantId->outletId when building `outletMap` and attributing revenue records. The `externalRevenue.outletId` field is already populated. Using outletId directly is simpler, avoids a redundant index query, and keeps the mutation interface clean. This is a non-functional deviation — the behavior is identical.
