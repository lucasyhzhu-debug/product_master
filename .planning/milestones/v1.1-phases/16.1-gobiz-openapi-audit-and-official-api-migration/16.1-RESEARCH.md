## Summary

The GoBiz Developer Portal at `developer.gobiz.com` provides an official OAuth2-based API for GoFood merchants. The official API covers **GoFood operations** (menu sync, order management, food-ready marking, outlet properties, promotions) and **Payment** (QRIS transaction creation and detail retrieval), with **webhook-based** event notifications for orders and payment settlements.

**Critical finding:** The official API does NOT provide the endpoints Frollie currently uses most. The current integration relies on reverse-engineered internal GoBiz endpoints (`api.gobiz.co.id/journals/search`, `cosmo/v1/orders/search`, portal proxy/63 dashboard) for **revenue/transaction data retrieval**. The official API has no equivalent -- it focuses on **receiving** GoFood orders via webhook (POS integration model), not **querying** historical transaction data. The payment API only covers QRIS transactions created through the API itself, not GoFood revenue settlements.

**Primary recommendation:** This phase should focus on: (1) complete documentation crawl of the official portal, (2) detailed gap analysis showing the mismatch between official capabilities and current usage, (3) migration of auth to OAuth2 client credentials where possible, (4) documentation of which endpoints must remain unofficial, and (5) future-looking docs on official capabilities we could adopt (webhook-based order flow, menu sync, stock management).

### Anti-Patterns to Avoid
- **Assuming official API covers everything:** The official API is for POS-style integration (receiving orders), not analytics/reporting (querying revenue). Do not try to force-fit official endpoints for revenue data.
- **Deleting working unofficial code prematurely:** Keep fallback code until migration is verified in production.
- **Mixing auth models:** Official API uses OAuth2 client_credentials; current uses browser cookie tokens. These are fundamentally different auth flows and may need to coexist.

## Common Pitfalls

### Pitfall 1: Auth Model Mismatch
**What goes wrong:** Attempting to use OAuth2 client_credentials tokens with the unofficial endpoints (journals/search, orders/search), which expect browser session tokens
**Why it happens:** The unofficial endpoints are internal GoBiz portal APIs, not part of the official partner API. They authenticate via browser cookies/sessions, not OAuth2.
**How to avoid:** Test each endpoint individually. The official OAuth2 token likely won't work with unofficial endpoints. The two auth models may need to coexist.
**Warning signs:** 401/403 errors when using official tokens on unofficial endpoints.

### Pitfall 2: Scope Confusion
**What goes wrong:** Assuming `payment:transaction:read` scope gives access to GoFood revenue data
**Why it happens:** The payment API covers QRIS transactions created through the API, not GoFood delivery payment settlements
**How to avoid:** The payment.transaction.settlement webhook provides GoFood revenue data, but only going forward (webhook, not historical query). For historical data, unofficial endpoints remain necessary.
**Warning signs:** Empty results when querying payment API for GoFood transactions.

### Pitfall 3: Incomplete Portal Crawl
**What goes wrong:** Missing documentation pages because the portal uses client-side rendering or nested navigation
**Why it happens:** JavaScript-rendered content may not be visible to simple HTTP fetches
**How to avoid:** Use Firecrawl (handles JS rendering). If pages are missing, manually check the navigation tree and use WebFetch on individual URLs.
**Warning signs:** Crawled pages have empty content or "loading" states.

### Pitfall 4: Production Token Conflict
**What goes wrong:** Registering for official API credentials (client_id/client_secret) disrupts existing browser-token-based integration
**Why it happens:** Unknown whether enabling official API integration changes how browser tokens work
**How to avoid:** Do NOT register for official API credentials in this phase unless explicitly safe. This phase is documentation and planning, not production migration.
**Warning signs:** Existing sync stops working after portal configuration changes.

### Pitfall 5: Over-Migration
**What goes wrong:** Trying to migrate endpoints that have no official equivalent, leading to data loss
**Why it happens:** Pressure to "go official" when the official API simply doesn't support the use case
**How to avoid:** The gap analysis document explicitly marks which endpoints CANNOT be migrated. Accept that unofficial endpoints are necessary for revenue data.
**Warning signs:** Planning to remove code that has no replacement.

## Code Examples

### Official OAuth2 Client Credentials Token Request
```typescript
// Source: https://developer.gobiz.com/docs/api/auth/direct-integration/
// Environment URLs:
//   Sandbox OAuth: https://integration-goauth.gojekapi.com/
//   Production OAuth: https://accounts.go-jek.com/
//   Sandbox API: https://api.partner-sandbox.gobiz.co.id/
//   Production API: https://api.gobiz.co.id/

const tokenResponse = await fetch("https://accounts.go-jek.com/oauth2/token", {
  method: "POST",
  headers: {
    "Content-Type": "application/x-www-form-urlencoded",
  },
  body: new URLSearchParams({
    client_id: "<APP_ID>",
    client_secret: "<APP_SECRET>",
    grant_type: "client_credentials",
    scope: "gofood:catalog:read gofood:order:read payment:transaction:read",
  }),
});

const { access_token, token_type, expires_in, scope } = await tokenResponse.json();
// access_token valid for ~3600 seconds (1 hour)
// token_type: "Bearer"
```

### Migration Feasibility Assessment

**CAN migrate (with partner registration):**
- Auth: OAuth2 client_credentials replaces manual cookie paste + 3-method cascade
- This is a MAJOR improvement -- eliminates the fragile token chain that breaks periodically

**CANNOT migrate (no official equivalent):**
- Historical revenue query (journals/search) -- official API has no historical transaction query endpoint
- Order item lookup (orders/search) -- official API delivers orders via webhook, doesn't allow querying past orders
- Dashboard analytics aggregation (proxy/63) -- no equivalent aggregate endpoint

**Could ADD (new capabilities):**
- Webhook-based real-time order tracking (forward-looking)
- Menu sync from Frollie to GoFood
- Stock status automation
- Order auto-acceptance

## Open Questions

1. **Partner Registration Requirements**
   - What we know: Official API requires `client_id` and `client_secret` from the developer portal
   - What's unclear: Whether Frollie's GoBiz account qualifies for partner API access, and whether enabling it affects existing browser-token flows
   - Recommendation: Document the registration process but do NOT register during this phase. Investigate in a follow-up phase.

2. **OAuth2 Token Compatibility with Unofficial Endpoints**
   - What we know: Official tokens use OAuth2 Bearer format; unofficial endpoints also use Bearer tokens
   - What's unclear: Whether an OAuth2 client_credentials token would be accepted by `journals/search` and `orders/search`
   - Recommendation: Flag for testing during migration. If OAuth2 tokens work on unofficial endpoints, auth migration is much simpler. If not, two token types must coexist.

3. **Webhook Requirements for Convex**
   - What we know: Official API uses webhooks (POST to your URL) for order events and payment settlements
   - What's unclear: Whether Convex HTTP endpoints can reliably receive and process GoBiz webhooks (HMAC verification, idempotency handling)
   - Recommendation: Convex `httpAction` should work. Document webhook payload formats for future implementation.

4. **Rate Limits on Official API**
   - What we know: Official docs mention rate limits exist
   - What's unclear: Specific rate limit values (requests/minute, etc.)
   - Recommendation: Document whatever is found in the portal. For unofficial endpoints, current 200ms delay between calls is conservative and should be maintained.

5. **Firecrawl MCP Availability**
   - What we know: User says Firecrawl MCP is set up and available
   - What's unclear: Whether it can handle developer.gobiz.com (may require authentication for some pages)
   - Recommendation: Try Firecrawl first. If it fails on authenticated pages, fall back to WebFetch on public documentation pages (all API reference pages appear publicly accessible).
