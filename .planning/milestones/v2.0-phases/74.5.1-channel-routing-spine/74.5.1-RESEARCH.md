# Phase 74.5: Unified Channel Integration Architecture — Research

**Researched:** 2026-04-19
**Domain:** Multi-channel revenue + inventory pipeline refactor (Convex backend, 8-source union, 5 live sync adapters, 2 consignment write paths, ~148K LOC codebase)
**Confidence:** HIGH (every factual claim in this document was verified against the working tree on commit `ad193c55` — see §Sources for file:line citations)

---

## Summary

The pre-existing 15-section design spec (2026-04-17) and 12-task TDD plan are **architecturally sound and still current** against the post-80.3 codebase with four narrow exceptions called out in §Stale-ness Audit. The spec correctly identifies the architecture and the split into two sub-phases is well-defined in 74.5-CONTEXT.md, but the research uncovered six things the plan must absorb:

1. **`externalSource` is 8 literals, not 7.** Spec/CONTEXT sometimes imply 7. `bigseller` + `consignment` + `gobiz` + `grabfood` + `internal` + `k3mart` + `shopee` + `tiktok` = 8. `channelDeductionEnabled` flag map must enumerate all 8. [VERIFIED: `convex/lib/externalSource.ts:10-19`, `convex/schema.ts:18-27`]

2. **K3Mart and Grabfood write revenue via `saveRevenue`, NOT `saveRevenueItems`.** They emit parent rows only — zero child `externalRevenueItems`. This is the Phase 80.2 "parent-only source" shape. Any saveRevenueItems-based deduct dispatch strategy must handle the case where K3Mart and consignment will BEGIN emitting children for the first time in 74.5.1. [VERIFIED: `convex/integrations/k3mart/adapter.ts:593`, `convex/integrations/grabfood/adapter.ts` (no saveRevenue* calls at all)]

3. **Grabfood adapter has NO revenue-writing code today.** Zero `saveRevenue`, zero `saveRevenueItems`, zero `processGofoodSales` references in `convex/integrations/grabfood/adapter.ts`. Grabfood OAuth works but it writes nothing to `externalRevenue`. Consequently "reroute grabfood through saveRevenueItems" is not a *refactor* — it's net-new integration work. [VERIFIED: grep of grabfood/adapter.ts returned zero matches for saveRevenue|processGofood|externalRevenue|productInventoryTransactions]

4. **`sourceToDisplayChannel` lives at `convex/reports/channelTaxonomy.ts` (not `convex/lib/channelTaxonomy.ts`)** — CONTEXT.md has the wrong path. Function is `sourceToDisplayChannel` (not `externalSourceToDisplayChannel`). Import path in every new admin UI file must resolve to reports/, not lib/. [VERIFIED: `find` command, file read]

5. **`productInventoryTransactions.transactionType` has 6 literals today** — `add | drawdown | gofood_sale | adjust | transfer | stock_count`. Spec says "channel_sale" is added and "gofood_sale" is dropped; that is correct. But `drawdown` (the `reserveStockForOrderInternal` direct-order fulfilment path) is NOT in scope and must NOT be touched. Any migration must preserve the other 5 literals. [VERIFIED: `convex/schema.ts:1012-1019`]

6. **GoFood deduction is wrapped in a silent try/catch — "Phase D failure should NOT fail the overall sync".** This is the OPPOSITE of saveRevenueItems atomicity. The spec mandates that in the new path, deduction failure rolls back revenue insert. This is a semantic change, not a no-op refactor. Regression snapshot tests must compare *successful* GoFood paths; failure semantics legitimately change. [VERIFIED: `convex/integrations/gobiz/adapter.ts:747-753` and `:1004-1009`]

**Primary recommendation:** Ship the spec's 5-layer design essentially as written, but fix the four stale references, expand the `channelDeductionEnabled` map to 8 sources, add an explicit "parent-only → parent+children" migration note for K3Mart/consignment, treat Grabfood as new integration (not refactor), and document the atomicity semantic change in the GoFood cutover runbook.

### Pattern 1: Atomic revenue + dispatch inside internalMutation

**What:** `saveRevenueItems` remains a single Convex `internalMutation`. Deduction dispatch lives inside the same mutation handler. Convex guarantees per-mutation atomicity — if `processChannelSaleInternal` throws on item N, all N-1 prior inserts AND the `externalRevenueItems` inserts roll back together.

**When to use:** Every channel sale that needs deduction in lockstep with revenue write.

**Example (merged from spec §6.2 + current impl at `convex/externalData/mutations.ts:787-826`):**

```typescript
async function saveRevenueItemsImpl(
  ctx: MutationCtx,
  args: SaveRevenueItemsArgs,
): Promise<{ ids: Id<"externalRevenueItems">[]; inserted: number; deducted: number; skipped: number }> {
  const revenue = await ctx.db.get(args.revenueId);
  if (!revenue) throw new Error(`Revenue record not found: ${args.revenueId}`);

  const settings = await ctx.db.query("productInventorySettings").first();
  const flagsForSource = settings?.channelDeductionEnabled?.[revenue.source] ?? false;

  const ids: Id<"externalRevenueItems">[] = [];
  let deducted = 0;
  let skipped = 0;

  for (const item of args.items) {
    // Existing dedup (preserved verbatim)
    if (item.externalItemId) {
      const existing = await ctx.db
        .query("externalRevenueItems")
        .withIndex("by_revenue", (q) => q.eq("revenueId", args.revenueId))
        .filter((q) => q.eq(q.field("externalItemId"), item.externalItemId))
        .first();
      if (existing) continue;
    }

    const id = await ctx.db.insert("externalRevenueItems", {
      /* existing fields preserved verbatim */
      revenueId: args.revenueId,
      source: revenue.source,
      externalItemId: item.externalItemId,
      productName: item.productName,
      unitPrice: item.unitPrice,
      quantity: item.quantity,
      totalPrice: item.totalPrice,
      variants: item.variants,
      linkedMenuProductId: item.linkedMenuProductId,
      isAutoMatched: item.isAutoMatched,
      matchConfidence: item.matchConfidence,
      createdAt: Date.now(),
      inventoryDeductedAt: undefined,  // NEW field, null on insert
    });
    ids.push(id);

    // NEW: audit-issue detection
    const issues = detectAuditIssuesForItem(ctx, revenue, item);
    if (issues.length > 0) await recordAuditIssues(ctx, issues);

    // NEW: deduction dispatch (flag-gated)
    if (!flagsForSource) { skipped++; continue; }
    if (!item.linkedMenuProductId) { skipped++; continue; }
    if (item.quantity <= 0) { skipped++; continue; }

    const event: ChannelSaleEvent = {
      source: revenue.source,
      occurredAt: revenue.transactionDate ?? revenue.periodStart,
      externalTransactionId: revenue.externalTransactionId ?? String(args.revenueId),
      externalItemId: item.externalItemId,
      outletId: revenue.outletId,
      menuProductId: item.linkedMenuProductId,
      externalProductCode: revenue.externalProductCode ?? item.productName,
      externalProductName: item.productName,
      quantity: item.quantity,
      unitPrice: item.unitPrice,
      totalPrice: item.totalPrice,
    };

    const result = await processChannelSaleInternal(ctx, event);
    if (result.deducted) {
      await ctx.db.patch(id, { inventoryDeductedAt: Date.now() });
      deducted++;
    } else {
      skipped++;
    }
  }

  return { ids, inserted: ids.length, deducted, skipped };
}
```

**Critical:** The outer `saveRevenueItems` internalMutation wrapper MUST preserve the current return shape (`result.ids` as `Id[]`) because `convex/bigsellerOrders/mutations.ts:288-292` destructures `.length` from it — same additive-return-type pattern Phase 80.2 established. Add `deducted`/`skipped` as new fields, leave `ids` intact.

### Pattern 3: Idempotent existence-based backfill loop (Phase 80.2 pattern)

**What:** The per-source backfill action pages through undeducted items by cursor, chunks 200 per mutation call, and the mutation's idempotency key is `inventoryDeductedAt IS NULL` — set on success, never touched after.

**Example (mirrors existing `useBackfillInternalRevenueItems` pattern at `src/hooks/convex/useUnlinkedBackfill.ts`):**

```typescript
// convex/productInventory/channelBackfill.ts
export const backfillChannelDeductionChunk = internalMutation({
  args: {
    source: externalSource,
    cursor: v.optional(v.id("externalRevenueItems")),
    limit: v.number(),
  },
  handler: async (ctx, args) => {
    // Index-scan by_source, forward, skipping already-deducted
    const pageQ = ctx.db
      .query("externalRevenueItems")
      .withIndex("by_source", (q) => q.eq("source", args.source));

    const items = await pageQ.take(args.limit * 3);  // over-fetch to filter
    let processed = 0, deducted = 0, skipped = 0;
    let nextCursor: Id<"externalRevenueItems"> | null = null;

    for (const item of items) {
      if (processed >= args.limit) { nextCursor = item._id; break; }
      if (item.inventoryDeductedAt != null) continue;  // idempotency key
      if (item.linkedMenuProductId == null) { skipped++; continue; }

      const revenue = await ctx.db.get(item.revenueId);
      if (!revenue) { skipped++; continue; }

      const event = buildEvent(revenue, item);
      const result = await processChannelSaleInternal(ctx, event);
      if (result.deducted) {
        await ctx.db.patch(item._id, { inventoryDeductedAt: Date.now() });
        deducted++;
      } else {
        skipped++;
      }
      processed++;
    }

    return { processed, deducted, skipped, nextCursor, isDone: nextCursor === null };
  },
});
```

### Anti-Patterns to Avoid

- **Dynamic `import()` in Convex modules** — lint rule enforces this: `"lint:convex": "! grep -rE \"await\\s+import\\s*\\(\" convex/ --include=\"*.ts\""`. Dynamic imports fail silently in prod (204 No Content) per project memory. All imports in new files must be static. [VERIFIED: package.json:22]
- **`ctx: { db: any }`** — breaks typed APIs. Use `MutationCtx` / `QueryCtx` / `ActionCtx` from `_generated/server`. [Per project memory]
- **Silent try/catch around deduction** — Current GoFood path has `try { processGofoodSales } catch { /* don't fail sync */ }`. The NEW path MUST NOT suppress deduction errors: atomicity requires the whole mutation to roll back so the sync engine can retry cleanly. Document this semantic change in the cutover runbook.
- **Freshness-based skip guards** — Phase 80.2 lesson: `if (!isNew) continue;` in a sync loop that gained an additive write block post-hoc creates permanent orphans. The internal adapter already learned this at `convex/integrations/internal/adapter.ts:150-156`. Any new sync loop in 74.5 must use existence checks (`if (await hasChildren(parent)) continue;`).
- **Per-source `if (source === X)` cascades without all 8 branches** — Phase 80.2 lesson: retroactive mapping cascade was gated to Shopee/TikTok and silently never ran for K3Mart. Every new source-switch must handle all 8 sources explicitly or refactor to source-neutral design.
- **Post-scan `.filter()` for index range bounds** — Per project memory: both bounds must be inside `.withIndex()`. `.filter()` after is a post-scan and will crash on large tables.
- **Mutating `menuProducts.productionType` / `productionUnits`** — Deprecated fields. Ball type must come from BOM (`menuProductComponents` + `componentTypes` with `category="production"`). Confirmed irrelevant here because `processChannelSaleInternal` deducts the menuProduct directly (not balls) — BOM resolution is downstream in reports/analytics, not in this deduction path. Do NOT attempt to deduct balls in 74.5 — that's a separate architecture.

## Common Pitfalls

### Pitfall 1: `externalRevenue.transactionDate` can be undefined for historical rows

**What goes wrong:** Backfill uses `event.occurredAt = revenue.transactionDate` to preserve historical timestamp. But `transactionDate` is `v.optional(v.number())` in the schema — nullable. If a historical parent row has `transactionDate == undefined`, the backfill writes `createdAt: undefined` which will explode or insert `NaN`.

**Why it happens:** Pre-Phase-20 internal orders had no `transactionDate` (the field didn't exist). Some old K3Mart rows may too.

**How to avoid:** In `buildEventFromRow`, fallback chain: `revenue.transactionDate ?? revenue.periodStart ?? revenue._creationTime`. Prefer `transactionDate` → `periodStart` → `_creationTime`. Document that `_creationTime` is inferior (it's insertion time, not business event time per project memory) but it's better than undefined.

**Warning signs:** Any `channel_sale` transaction with a `createdAt` matching its insertion timestamp (clock-skewed with `_id._creationTime`) after backfill — suggests fallback triggered.

[VERIFIED: `convex/schema.ts:1121` — `transactionDate: v.optional(v.number())`]

---

### Pitfall 2: Consignment settlement items don't exist in normalized form

**What goes wrong:** `createSettlement` receives `totalRevenue` as a lump sum, not an item breakdown. Refactoring it to emit `ChannelSaleEvent[]` via `saveRevenueItems` requires splitting the lump into per-product rows — and the current mutation signature doesn't ask for that.

**Why it happens:** The original consignment UI collects `totalRevenue` only; per-product breakdown isn't captured in the form today. The "stretch" consignment reporting extension in 74.5.2 depends on this breakdown existing.

**How to avoid:** Either (a) extend `createSettlement` signature to accept optional per-product breakdown; emit items only when breakdown provided; flag-gate the deduction; OR (b) require the breakdown before flag-flip. **Recommendation: (a) — make breakdown optional; if not supplied, write the parent row as today (no item rows → no deduction), and gate the consignment flag flip on "admins have started capturing per-product breakdowns in the UI." Adds a new UI task to 74.5.2.**

**Warning signs:** Consignment settlements appearing in audit report as `aggregate_no_items` (new audit issue type if (b)) or `malformed_item` (if (a) and breakdown is expected but missing).

[VERIFIED: `convex/consignment/mutations.ts:153-222` — current `createSettlement` has no `items` argument]

---

### Pitfall 3: BigSeller `source: "bigseller"` has no items today

**What goes wrong:** Row 4 of the migration matrix above. BigSeller's non-Shopee/TikTok pipeline writes parent rows only; `saveRevenueItems` emit is gated to `platform === "shopee" || platform === "tiktok"` at `convex/integrations/bigseller/sync.ts:804`. "Backfill bigseller" in 74.5.2 will find zero rows.

**Why it happens:** BigSeller aggregates marketplace data where item breakdown isn't always available. Phase 79 scoped the item-level emit to the two platforms where SKU-level data exists.

**How to avoid:** Either exclude `bigseller` from the feature-flag map entirely, or include it but treat the flag as "no-op" permanently. **Recommendation: exclude `bigseller` from `channelDeductionEnabled` union AND from the six backfill buttons. Document as "bigseller source captures aggregate data only; per-item deduction not applicable."** Reduces the UI surface and prevents admins from thinking they can toggle it.

**Warning signs:** Admin attempts to flip `bigseller` flag and nothing happens (zero items to dispatch on).

[VERIFIED: `convex/integrations/bigseller/sync.ts:804-866` — emit branch conditional on platform]

---

### Pitfall 4: Mutation time limit on historical backfill for high-volume channels

**What goes wrong:** GoFood and Shopee likely have thousands of historical `externalRevenueItems`. A naive 200-chunk loop calls `processChannelSaleInternal` 200× per mutation; each calls `stockTracker.getStock` (one DB read) + `resolveChannelRoute` (one DB read) + `productInventoryTransactions.insert` (one write). That's 600+ DB ops per mutation — close to the 1 MB write limit if stock docs are large or the 16s time limit if queries hit cold indexes.

**Why it happens:** Convex has a soft limit of ~16s per mutation and 8 MB read/write bandwidth. Phase 78 mitigates with the stockTracker cache (one read per unique product×location), but backfill spans thousands of distinct products — cache hit rate drops.

**How to avoid:** Keep the 200-chunk ceiling from spec §9. If 200 still times out empirically, the action loop can shrink the chunk. Also: precompute the `resolveChannelRoute` result per (source, outletId, menuProductId) triple in the action before calling the mutation, and pass resolved `storageLocationId` as an argument — moves the query cost out of the mutation. **Don't ship this optimization unless 200 fails.**

**Warning signs:** Backfill action errors "Function execution took too long" or bandwidth exceeded.

---

### Pitfall 5: Audit issue detection on read-heavy items field runs on every `saveRevenueItems` call

**What goes wrong:** `detectAuditIssuesForItem` needs to check: is SKU mapped? is mapping stale? is item malformed? is transaction a duplicate? is parent orphan? Each check may hit a different index. Running all 5 on every item of every revenue write = significant read amplification on the hot path.

**Why it happens:** Spec §8.1 places detection inside `saveRevenueItems`. During sync, that's thousands of items across a batch.

**How to avoid:** Cheap checks inline (is `linkedMenuProductId == null`? → `unmapped_sku`, no DB call; is `quantity <= 0 || totalPrice < 0`? → `malformed_item`, no DB call). Expensive checks (stale mapping lookup, duplicate transaction scan, orphan parent check) should run ONLY in `runFullAudit`, not inline. Inline detection catches the common cases cheaply; full audit catches the rest.

**Warning signs:** `saveRevenueItems` latency increases noticeably after 74.5.1 deployment even with all flags off.

---

### Pitfall 6: `_creationTime` vs business event time confusion in reports

**What goes wrong:** Reports that filter by `createdAt` expect it to be the sale's business date. Backfilled rows set `createdAt = revenue.transactionDate` (historical). But if a report also falls back to `_creationTime`, mixed backfill and live-write rows will have inconsistent ordering.

**Why it happens:** Per project memory: `_creationTime` is insertion time, NOT business event time.

**How to avoid:** Always use explicit `createdAt`; never fall back to `_creationTime` in reports. Document in `docs/API_REFERENCE.md` update.

---

### Pitfall 7: Audit issue taxonomy is incomplete without `aggregate_no_items` + `missing_routing`

**What goes wrong:** Spec's 5 issue types (`unmapped_sku`, `stale_mapping`, `malformed_item`, `duplicate_transaction`, `orphan_item`) don't cover: (a) parent rows that structurally can't have children (BigSeller aggregate, consignment without breakdown captured), (b) items whose routing can't resolve because no `channelRouting` row exists for that source.

**Why it happens:** The 5 types come from the item-centric view; aggregate and routing-gap errors are source-level or config-level.

**How to avoid:** Extend taxonomy to 7 types: add `aggregate_no_items` (source writes parents but not children; informational) and `missing_routing` (deduction would throw `CHANNEL_ROUTING_NOT_CONFIGURED`; detected during backfill dry-run). **Recommendation: ship with 5 as spec says; add `missing_routing` only if routing gaps turn out to be common during the 74.5.1 QA pass.**

**Warning signs:** `CHANNEL_ROUTING_NOT_CONFIGURED` throws during backfill that weren't caught by audit.

## Code Examples

### Example 1: `resolveChannelRoute` — 5-tier precedence with single-round-trip indexes

```typescript
// convex/productInventory/channelRouting.ts
import type { QueryCtx, MutationCtx } from "../_generated/server";
import type { Id } from "../_generated/dataModel";
import type { ExternalSource } from "../lib/externalSource";

export const CHANNEL_ROUTING_NOT_CONFIGURED = "CHANNEL_ROUTING_NOT_CONFIGURED";

export async function resolveChannelRoute(
  ctx: QueryCtx | MutationCtx,  // accept either — Discretion D-*
  params: {
    source: ExternalSource;
    outletId?: Id<"externalOutlets">;
    menuProductId?: Id<"menuProducts">;
  },
): Promise<Id<"storageLocations">> {
  const { source, outletId, menuProductId } = params;

  // Tier 1: (source, outlet, product) — most specific
  if (outletId && menuProductId) {
    const row = await ctx.db
      .query("channelRouting")
      .withIndex("by_source_outlet_product", (q) =>
        q.eq("source", source).eq("outletId", outletId).eq("menuProductId", menuProductId),
      )
      .first();
    if (row) return row.storageLocationId;
  }

  // Tier 2: (source, outlet), product unspecified
  if (outletId) {
    const row = await ctx.db
      .query("channelRouting")
      .withIndex("by_source_outlet", (q) => q.eq("source", source).eq("outletId", outletId))
      .filter((q) => q.eq(q.field("menuProductId"), undefined))
      .first();
    if (row) return row.storageLocationId;
  }

  // Tier 3: (source, product), outlet unspecified
  if (menuProductId) {
    const row = await ctx.db
      .query("channelRouting")
      .withIndex("by_source_product", (q) => q.eq("source", source).eq("menuProductId", menuProductId))
      .filter((q) => q.eq(q.field("outletId"), undefined))
      .first();
    if (row) return row.storageLocationId;
  }

  // Tier 4: source default (isDefault = true, no outlet, no product)
  const def = await ctx.db
    .query("channelRouting")
    .withIndex("by_source", (q) => q.eq("source", source))
    .filter((q) =>
      q.and(
        q.eq(q.field("isDefault"), true),
        q.eq(q.field("outletId"), undefined),
        q.eq(q.field("menuProductId"), undefined),
      ),
    )
    .first();
  if (def) return def.storageLocationId;

  // Tier 5: throw
  throw new Error(`${CHANNEL_ROUTING_NOT_CONFIGURED}: source=${source}, outlet=${outletId ?? "-"}, product=${menuProductId ?? "-"}`);
}
```

**Note on index bounds (project memory):** both bounds of each `.withIndex()` are inside the `.withIndex()` call. The Tier 2/3 `.filter()` on `undefined` post-scans at most a few matching rows (per source, per outlet or per product) — acceptable because the filter narrows a pre-indexed page, not a full table scan.

### Example 2: `processChannelSaleInternal` — reuses Phase 78 helpers verbatim

```typescript
// convex/productInventory/channelSale.ts
import type { MutationCtx } from "../_generated/server";
import type { Doc, Id } from "../_generated/dataModel";
import type { ChannelSaleEvent } from "../integrations/_shared/channelSaleEvent";
import { resolveChannelRoute } from "./channelRouting";
import { resolveSubstitutionPlan } from "./substitution";
import { createStockTracker, type StockTracker } from "./stockTracker";

export async function processChannelSaleInternal(
  ctx: MutationCtx,
  event: ChannelSaleEvent,
  tracker?: StockTracker,  // optional — caller can pass shared tracker across a batch
): Promise<
  | { deducted: true; locationId: Id<"storageLocations">; transactionId: Id<"productInventoryTransactions"> }
  | { deducted: false; skipReason: "unmapped_sku" | "zero_quantity" | "already_deducted" }
> {
  if (!event.menuProductId) return { deducted: false, skipReason: "unmapped_sku" };
  if (event.quantity <= 0) return { deducted: false, skipReason: "zero_quantity" };

  const locationId = await resolveChannelRoute(ctx, {
    source: event.source,
    outletId: event.outletId,
    menuProductId: event.menuProductId,
  });

  const local = tracker ?? createStockTracker(ctx);

  const menuProduct = await ctx.db.get(event.menuProductId);
  if (!menuProduct) return { deducted: false, skipReason: "unmapped_sku" };

  const directStock = await local.getStock(event.menuProductId, locationId);
  let sourceProduct: Doc<"menuProducts"> | null = null;
  let subStock = null;
  if (menuProduct.fulfillFromProductId && menuProduct.fulfillMultiplier) {
    sourceProduct = await ctx.db.get(menuProduct.fulfillFromProductId);
    if (sourceProduct) subStock = await local.getStock(menuProduct.fulfillFromProductId, locationId);
  }
  const plan = resolveSubstitutionPlan(event.quantity, directStock.runningQty, menuProduct, sourceProduct);

  const externalRef = `${event.externalTransactionId}${event.externalItemId ?? ""}`;
  let txId: Id<"productInventoryTransactions"> | undefined;

  if (plan.directUnits > 0) {
    const prev = directStock.runningQty;
    const next = prev - plan.directUnits;
    directStock.runningQty = next;
    txId = await ctx.db.insert("productInventoryTransactions", {
      menuProductId: event.menuProductId,
      locationId,
      transactionType: "channel_sale",
      source: event.source,
      quantity: -plan.directUnits,
      previousQuantity: prev,
      newQuantity: next,
      externalRef,
      performedBy: `system:${event.source}_sync`,
      createdAt: event.occurredAt,  // ★ historical, NOT Date.now()
    });
  }

  if (plan.needsSubstitution && plan.substituteUnits > 0 && sourceProduct && subStock) {
    const prev = subStock.runningQty;
    const next = prev - plan.substituteUnits;
    subStock.runningQty = next;
    await ctx.db.insert("productInventoryTransactions", {
      menuProductId: sourceProduct._id,
      locationId,
      transactionType: "channel_sale",
      source: event.source,
      quantity: -plan.substituteUnits,
      previousQuantity: prev,
      newQuantity: next,
      externalRef,
      performedBy: `system:${event.source}_sync`,
      createdAt: event.occurredAt,
    });
  }

  if (!tracker) await local.flush(event.occurredAt);  // flush only if we own the tracker

  return { deducted: true, locationId, transactionId: txId! };
}
```
