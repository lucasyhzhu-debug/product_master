<domain>
## Phase Boundary

The Analytics page (`/analytics`) double-counts every Direct/WhatsApp/Instagram/Consignment-native order because `loadExternalStream` in `convex/reports/unitEconomics.ts` reads both the native `orders`+`orderItems` stream AND the `externalRevenue[source="internal"]` mirror of those same orders created by `syncInternalOrders`. Every Direct channel KPI on Analytics is inflated roughly 2× relative to the source-of-truth Sales Aggregation page. This phase adds the one-line R5 skip rule (specified in the Phase 80 Task 4b staff-review addendum but never committed to code) and adds regression-test coverage to prevent future callers of `loadFilteredData` from re-introducing the bug.

**Scope:** Backend-only fix to the Unit Economics analytics loader. No UI changes. No schema changes. Regression tests added to every downstream query that consumes `loadFilteredData`.

**Out of scope:**
- Fixing Sales Aggregation page (it is the source of truth — already correct)
- Changing the internal-mirror write path in `syncInternalOrders` (the mirror is required for Sales Aggregation)
- Any frontend changes — Analytics KPIs will simply drop to correct values once the loader is fixed
- Production data backfill — there is nothing to backfill; the loader runs live per query

</domain>

<decisions>
## Root-Cause Evidence (from debug session)

### The double-count mechanism
1. `convex/integrations/internal/adapter.ts:79-153` — `syncInternalOrders` action INSERTs a mirror row into `externalRevenue[source="internal"]` (+ child `externalRevenueItems`) for every revenue-countable native `orders` row.
2. `convex/reports/unitEconomics.ts:100-229` — `loadExternalStream` reads ALL externalRevenue rows filtered only by `transactionType === "sales"`. It does NOT skip `source === "internal"`.
3. `convex/reports/unitEconomics.ts:240-362` — `loadFilteredData` UNIONs the native `orders`+`orderItems` stream with the external stream. Direct orders therefore appear TWICE: once via native path, once via internal-mirror path.
4. `convex/reports/channelTaxonomy.ts:74` — `sourceToDisplayChannel("internal")` returns `"Direct"`. Same display channel as native `whatsapp`/`instagram` orders, so the double-count concentrates on the Direct channel.

### Math verification (all three deltas self-consistent)
| Delta | Observed | Explanation |
|---|---|---|
| Revenue | 517,406,822 − 387,470,822 = **Rp 129,936,000** | Native `orderItems.lineTotal` sum over 265 duplicate direct orders |
| Units | 9,493 − 8,876 = **617 balls** | BOM-expanded duplicate count of those 265 orders' items |
| Orders | 2,629 − 2,364 = **265 orders** | One `orderWeight` per native direct order whose internal mirror is also counted |

### R5 rule was spec'd but never shipped
Commit `59069988 fix(80): apply Task 4b staff-review fixes — gobiz is GoFood, R5 skip internal only` (2026-04-14) is on main but only modified plan documents (`80-01-PLAN.md`, `80-03-PLAN.md`, `80-CONTEXT.md`) and the staffreview doc. It did NOT touch `convex/reports/unitEconomics.ts`. `git grep 'source === "internal"' convex/reports/unitEconomics.ts` returns zero hits.

### Sales Aggregation page is correct (reference behaviour)
`convex/externalData/queries.ts:520-621` and `convex/externalData/helpers/dashboardHelpers.ts:15-141` read ONLY `externalRevenue` — they never union the native `orders` stream. The internal-mirror rows represent the one-and-only count of Direct orders in that pipeline. Balls derivation in `convex/externalData/helpers/lifetimeHelpers.ts:77-105` uses the same `externalRevenue`-only approach.

</decisions>

<specifics>
## Fix Architecture (single change + symmetric regression coverage)

### Primary code change
Inside `loadExternalStream` at `convex/reports/unitEconomics.ts` around lines 100–229, add (exact placement TBD by research — likely inside the per-row loop near line 126 where the returns/delta_inferred filter lives):

```ts
if (r.source === "internal") continue;  // R5 — internal is the orders twin
```

This single line is the entire production-code change. `loadExternalStream` is called from `loadFilteredData`, which is the shared loader for every analytics query, so one change propagates to all downstream KPIs.

### Call sites that inherit the fix (from parent-phase plan Tests 12/12b/17)
Every query that calls `loadFilteredData` benefits from the fix. Research will enumerate all of them from `convex/reports/unitEconomics.ts`. Known list at time of debug:
1. `kpiSummary` — headline Revenue/Units/Orders/AOV
2. `byWeekday` — weekday volume
3. `dayHourHeatmap` — hour-of-day heatmap
4. `channelEconomics` — per-channel take-rate + unit economics
5. `volumeByType` — big-ball vs mid-ball volume
6. `unitsPerTxnByChannel` — units per transaction by channel
7. `aovByChannel` — AOV by channel
8. `skuPareto` — top-SKU Pareto
9. `skuChannelMatrix` — SKU × channel cross-tab
10. `channelMomentum` — WoW/MoM momentum
11. `rollingTrend` — rolling trend chart

### Test symmetry requirement
Research must confirm that every query above sees the dedup. Plan will add three regression-test tiers:
- **Test 12 (internal skip)** — insert a native direct order, run `syncInternalOrders`, assert `kpiSummary.orders === 1` (not 2)
- **Test 12b (gobiz contributes)** — insert a gobiz=GoFood externalRevenue row, assert it IS counted (negative-test: guards against over-aggressive skip)
- **Test 17 (internal-skip symmetry)** — iterate every query that calls `loadFilteredData` and assert each sees `source="internal"` exactly zero times

### No data work required
The bug is in the aggregator, not the data. Once the loader skips `source="internal"`, Analytics numbers drop to correct values on the next reactive query — no migration, no backfill, no cache invalidation (Convex queries auto-refresh).

</specifics>
