## Architecture Patterns

### Pattern 1: protectedQuery with Role Restriction
**What:** Backend query wrapper that validates session + role before handler runs.
**When to use:** Any admin-only query.
**Example:**
```typescript
// Source: convex/expenses/queries.ts lines 76-108 (already implemented)
export const listAllExpenses = protectedQuery({
  roles: ["admin"],
  args: { status: v.optional(expenseStatusValidator) },
  handler: async (ctx, args) => {
    // ... fetch + join submitter names
  },
});
```
[VERIFIED: convex/lib/functions.ts lines 91-100]

### Pattern 2: nameMap Join for Submitter Names
**What:** Collect unique user IDs from results, batch-fetch users, build `Map<string, string>` for name lookup.
**When to use:** Any query that needs to display user names alongside records they own.
**Example:**
```typescript
// Source: convex/expenses/queries.ts lines 96-106 (already implemented)
const userIds = [...new Set(expenses.map((e) => e.submittedBy))];
const users = await Promise.all(userIds.map((id) => ctx.db.get(id)));
const nameMap = new Map<string, string>();
for (const user of users) {
  if (user) nameMap.set(user._id, user.name);
}
return expenses.map((e) => ({
  ...e,
  submitterName: nameMap.get(e.submittedBy) ?? "Unknown",
}));
```
[VERIFIED: same pattern at convex/expenses/queries.ts lines 242-248 (listPendingForApproval)]

### Pattern 3: Mutually Exclusive Skip-Based Hooks
**What:** Two hooks both called unconditionally (React rules), one active via args, other skipped via `"skip"`.
**When to use:** When same component needs different data sources based on user role.
**Example:**
```typescript
// Source: src/hooks/convex/useExpenses.ts lines 27-39 (already implemented)
export function useMyExpenses(status?: ExpenseStatus, enabled: boolean = true) {
  return useSessionQuery(
    api.expenses.queries.listMyExpenses,
    enabled ? (status ? { status } : {}) : "skip"
  );
}
export function useAllExpenses(status?: ExpenseStatus, enabled: boolean = true) {
  return useSessionQuery(
    api.expenses.queries.listAllExpenses,
    enabled ? (status ? { status } : {}) : "skip"
  );
}
```
[VERIFIED: codebase uses `"skip"` in 10+ hooks]

### Pattern 4: Mine-First Sorting with useMemo
**What:** `useMemo` sorts results with own-first comparator, preserving `createdAt` desc within groups.
**When to use:** Admin views where own items should pin to top.
**Example:**
```typescript
// Source: src/pages/MyExpenses.tsx lines 76-84 (already implemented)
const expenses = useMemo(() => {
  if (!rawExpenses || !isAdmin || !user) return rawExpenses;
  return [...rawExpenses].sort((a, b) => {
    const aMine = a.submittedBy === user.userId ? 0 : 1;
    const bMine = b.submittedBy === user.userId ? 0 : 1;
    if (aMine !== bMine) return aMine - bMine;
    return b.createdAt - a.createdAt;
  });
}, [rawExpenses, isAdmin, user]);
```
[VERIFIED: same pattern at src/components/orders/KanbanColumn.tsx lines 56-63]

### Pattern 5: Blue Ring Highlight with cn() Merge
**What:** `ring-2 ring-blue-400` class applied conditionally, merged via `cn()`. Selection ring takes precedence via ordering in `cn()` args.
**When to use:** Visual ownership indicators on cards.
**Example:**
```typescript
// Source: src/components/expenses/ExpenseCard.tsx line 26 (already implemented)
<div className={cn(
  "border rounded-lg p-4 cursor-pointer hover:bg-accent/50 transition-colors",
  highlightMine && isMine && "ring-2 ring-blue-400",
  className  // selection ring passed here overrides mine highlight
)} ... />
```
[VERIFIED: same pattern at src/components/orders/KanbanCard.tsx lines 104-112]

### Anti-Patterns to Avoid
- **Running both queries for admin:** Admin should skip `useMyExpenses`, not run both subscriptions. Already correctly implemented with `enabled` param. [VERIFIED: MyExpenses.tsx line 70-71]
- **Hooks after conditional returns:** All hooks called before any `if` checks. [VERIFIED: MyExpenses.tsx lines 56-93 -- all hooks before JSX return]
- **Inline void button on cards:** Decision D-09 explicitly says void is in timeline panel only. [VERIFIED: CONTEXT.md]

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Role-restricted queries | Custom auth check in handler | `protectedQuery({ roles: ["admin"] })` | Session validation, role check, typed `ctx.user` automatic [VERIFIED: convex/lib/functions.ts] |
| User name display | Separate name lookup query | `nameMap` join in query response | Single round-trip, established pattern [VERIFIED: queries.ts] |

## Common Pitfalls

### Pitfall 1: Ring Priority Conflict
**What goes wrong:** When an expense card is both "mine" (blue ring) and "selected" (primary ring), both rings try to render.
**Why it happens:** Two `ring-*` classes in the same element.
**How to avoid:** Pass selection ring via `className` prop (last arg to `cn()`), which overrides the mine highlight. Tailwind's `cn()` (via clsx + twMerge) resolves the conflict. Already correctly implemented.
**Warning signs:** Both blue and primary rings visible simultaneously.
[VERIFIED: ExpenseCard.tsx line 26 -- className is last arg to cn()]

### Pitfall 2: Admin Editing Others' Draft Expenses
**What goes wrong:** Admin clicks another user's draft expense and navigates to the edit form instead of opening timeline.
**Why it happens:** Original click handler navigated all draft expenses to edit form.
**How to avoid:** Check ownership before navigating to edit: `expense.status === "draft" && (!isAdmin || expense.submittedBy === user?.userId)`. Already correctly implemented.
**Warning signs:** Admin seeing edit form for expenses they don't own.
[VERIFIED: MyExpenses.tsx lines 100-101]

### Pitfall 3: ApprovalActions on Terminal Statuses
**What goes wrong:** Void button appears on already-voided or reimbursed expenses.
**Why it happens:** `ApprovalActions` component doesn't filter terminal statuses.
**How to avoid:** Gate `ApprovalActions` rendering with `selectedExpense.status !== "voided" && selectedExpense.status !== "reimbursed"`. Already correctly implemented.
**Warning signs:** Void button visible on voided expenses in timeline panel.
[VERIFIED: MyExpenses.tsx line 193]

### Pitfall 4: Full Table Collect Scaling
**What goes wrong:** `listAllExpenses` with no status filter does full table `collect()`.
**Why it happens:** No paginate/limit on unfiltered path.
**How to avoid:** For now, expense table is small (< 500 rows). A `// TODO: paginate if >500 rows` comment marks the tech debt. Not blocking for current scale.
**Warning signs:** Slow query response times, Convex function timeout.
[VERIFIED: queries.ts line 90 -- TODO comment present]
