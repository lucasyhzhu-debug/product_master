# Phase 53.1: Fix GoBiz Promo Discount Net Revenue Inflation - Research

**Researched:** 2026-03-15
**Domain:** GoBiz revenue sync + Sales Analytics dashboard aggregation
**Confidence:** HIGH

## Summary

This is a HAR-verified bug fix with two related issues: (1) the dashboard aggregation helper recalculates net revenue from components instead of using the already-correct stored `revenueNet` field, and (2) the GoBiz journal sync does not extract `variables.voucher_amount` (merchant's campaign promo discount share) so promo costs are invisible in Sales Analytics.

The root cause analysis is fully validated against 13 real orders (9 promo, 4 non-promo) with a 100% formula match rate. The `externalRevenue` table already has both the correct `revenueNet` value (from `transaction_share[0].amount / 100`) and a `promoBurn` field (optional number, currently only populated by the unused dashboard API path). No schema changes are needed.

**Primary recommendation:** Fix Bug 1 first (use stored `revenueNet` instead of recalculating) as it immediately corrects all net revenue values. Then fix Bug 2 (extract `voucher_amount` during sync and display in UI) for promo discount visibility.

### Pattern: aggregatePlatformChannel (the function with the bug)

```typescript
// CURRENT (BUGGY): Recalculates net from components
function aggregatePlatformChannel(channelRecords: Doc<"externalRevenue">[]) {
  let gross = 0, commission = 0, adBurn = 0, promoBurn = 0, txns = 0;
  for (const r of channelRecords) {
    gross      += r.revenueGross    ?? 0;
    commission += r.commission      ?? 0;
    adBurn     += r.adBurn          ?? 0;
    promoBurn  += r.promoBurn       ?? 0;
    txns       += r.transactionCount ?? 0;

  return { gross, net, txns, commission, adBurn, promoBurn };
}
```

This function is used for ALL non-internal sources (gobiz, k3mart, bigseller, shopee, tiktok). The fix must work for all of them.

### Key Insight: BigSeller/K3Mart Safety

BigSeller records set `revenueNet = order.platformIncome` (the correct net). K3Mart records set `revenueNet = txn.profit`. For both platforms, `promoBurn` is never set (undefined/null). So:
- After Bug 1 fix: their net will come from `revenueNet` directly -- CORRECT
- The `revenueNet` fallback to `revenueGross` handles any edge case where `revenueNet` is null

### Frontend Display Pattern: ChannelSummary

The `ChannelSummary` component currently shows: Gross, Net, Transactions, AOV per channel. The `PeriodData` type already has `totalPromoBurn` at the top level but channels don't carry promo data. The `HeroCards` component already displays `totalPromoBurn` when > 0 under the "Commissions Paid" card.

**Recommendation for promo display:** Extend the per-channel data shape to include `promoBurn` so ChannelSummary can show a promo deduction line between Gross and Net for channels that have promo data. Alternatively, show promo as a sub-line under Net (simpler, no type change needed for channels).

## Common Pitfalls

### Pitfall 1: Breaking BigSeller/K3Mart net calculations
**What goes wrong:** Changing aggregation logic affects all non-internal channels, not just gobiz.
**Why it happens:** `aggregatePlatformChannel` processes ALL platform sources.
**How to avoid:** Use `revenueNet` with fallback to `revenueGross` (not to the recalculated formula). BigSeller and K3Mart both correctly populate `revenueNet`, so the fix is safe for them. Verify with: BigSeller has `revenueNet = platformIncome`, K3Mart has `revenueNet = profit`.
**Warning signs:** BigSeller/K3Mart channels showing different net values after the fix.

### Pitfall 2: Centesimal vs IDR confusion in voucher_amount
**What goes wrong:** Storing voucher_amount raw (centesimal) instead of dividing by 100.
**Why it happens:** Journal API amounts are in centesimal IDR (x100). The existing `extractJournalMetrics()` divides gross, net, commission by 100 -- the new voucher_amount extraction must do the same.
**How to avoid:** Apply `/ CENTESIMAL_DIVISOR` consistently. The HAR analysis confirms `variables.voucher_amount` is centesimal (2450000 = 24,500 IDR).
**Warning signs:** promoBurn values 100x larger than expected.

### Pitfall 3: Null promoBurn for existing records
**What goes wrong:** After deploying Bug 2 fix, old records still have `promoBurn = undefined`. If the aggregation sums promoBurn for display, old promo orders will show zero promo.
**Why it happens:** Bug 2 only affects NEW syncs. Existing gobiz records were saved without promoBurn.
**How to avoid:** Accept this limitation -- Bug 1 fix (using revenueNet) makes the net correct regardless. PromoDiscount visibility will only be accurate for records synced after the fix. If historical accuracy is needed, a data migration or resync would be required (out of scope).
**Warning signs:** Promo burn total being lower than expected for historical periods.

### Pitfall 4: Channels array type not carrying promo data
**What goes wrong:** The `PeriodData.channels` array type is `{ source, displayName, gross, net, transactions }` -- no promo field. Adding promo data requires updating both the backend return type and the frontend type.
**Why it happens:** The channels type was designed without per-channel deduction breakdown.
**How to avoid:** Either (a) extend the channels array item type to include `promoBurn` (requires updating `PeriodData` and `ChannelSummary`), or (b) compute promo as `gross - net - commission` at the frontend display level (simpler, no type change, but less precise for non-promo deductions like adBurn).
**Recommendation:** Option (a) -- extend the type. It's a small change and more correct.

### Pitfall 5: aggregateJournalMetrics doesn't aggregate promoDiscount
**What goes wrong:** `aggregateJournalMetrics()` in `gobiz/helpers.ts` aggregates gross/net/commission but not promoDiscount. If promoDiscount is added to JournalMetrics but not to the aggregate, the adapter's logging won't show promo totals.
**Why it happens:** The aggregate function was written before promo extraction was considered.
**How to avoid:** Add promoDiscount to the aggregate function's accumulator and return type. This is used in the adapter's console.log output and for the daily summary.

## Code Examples

### Bug 1 Fix: Use stored revenueNet in aggregatePlatformChannel

```typescript
// convex/externalData/helpers/dashboardHelpers.ts
// Source: HAR-verified fix from debug analysis

function aggregatePlatformChannel(channelRecords: Doc<"externalRevenue">[]) {
  let gross = 0, net = 0, commission = 0, adBurn = 0, promoBurn = 0, txns = 0;
  for (const r of channelRecords) {
    gross      += r.revenueGross    ?? 0;
    // Use stored revenueNet (correct for all platforms) with fallback
    net        += r.revenueNet      ?? (r.revenueGross ?? 0);
    commission += r.commission      ?? 0;
    adBurn     += r.adBurn          ?? 0;
    promoBurn  += r.promoBurn       ?? 0;
    txns       += r.transactionCount ?? 0;
  }
  // net is now the sum of stored revenueNet values, NOT recalculated
  return { gross, net, txns, commission, adBurn, promoBurn };
}
```
