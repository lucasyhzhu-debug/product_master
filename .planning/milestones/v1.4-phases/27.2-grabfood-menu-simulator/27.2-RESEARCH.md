# Phase 27.2: GrabFood Menu Simulator - Research

**Researched:** 2026-02-27
**Domain:** GrabFood Partner API menu management + Convex full-stack UI
**Confidence:** HIGH

## Summary

This phase builds a standalone `/grabfood-menu` page that simulates the GrabFood customer-facing menu. The admin pulls the current menu state from internal data (externalProductMappings), edits items inline (name, price, description, availability, photos), adds new items from internal menu products, and pushes changes to GrabFood via the Partner API batch update + notification two-step flow.

The codebase already has substantial GrabFood infrastructure from Phases 27 and 27.1: OAuth2 token resolution (`resolveToken`), batch availability update (`batchUpdateAvailability`), menu notification (`notifyMenuUpdate`), webhook handlers including the GET /menu endpoint that builds Section-based JSON from `externalProductMappings`, and the `updateProductMappingFields` mutation for price/availability. The main work is: (1) a new `grabfoodMenuItems` table for storing GrabFood-specific overrides (name, description, photos, sequence) beyond what `externalProductMappings` currently holds, (2) a GrabFood-app-like visual preview UI, (3) "add item from menu products" flow, (4) push-to-GrabFood with diff summary and confirmation, (5) photo upload via Convex file storage with write-back to menu products.

**Primary recommendation:** Extend the existing `externalProductMappings` table with additional GrabFood-specific fields OR create a dedicated `grabfoodMenuItems` table. The latter is cleaner because the simulator needs fields (description, photos, sequence, grabfoodName) that are GrabFood-specific and would pollute the shared mapping table. Use Convex file storage (existing pattern from feedback module) for photo upload.

### Pattern 1: GrabFood Menu Data Model
**What:** A `grabfoodMenuItems` table stores GrabFood-specific overrides per item.
**When to use:** Every menu item displayed in the simulator.

```typescript
// convex/schema.ts addition
grabfoodMenuItems: defineTable({
  menuProductId: v.id("menuProducts"),           // Link to internal product
  grabfoodItemId: v.optional(v.string()),         // GrabFood's item ID (from existing mapping or generated)
  grabfoodName: v.string(),                       // Override name for GrabFood
  grabfoodDescription: v.optional(v.string()),    // Override description
  grabfoodPrice: v.number(),                      // Price in IDR (integer, no decimals)
  isAvailable: v.boolean(),                       // Manual availability toggle
  photoStorageId: v.optional(v.id("_storage")),   // Convex file storage ID for uploaded photo
  photoUrl: v.optional(v.string()),               // External photo URL (from GrabFood pull)
  sequence: v.number(),                           // Display order
  createdAt: v.number(),
  updatedAt: v.number(),
})
  .index("by_menu_product", ["menuProductId"])
  .index("by_sequence", ["sequence"]),
```

**Rationale:** Separate from `externalProductMappings` because:
1. The simulator needs fields (description, photos, sequence, name override) that are UI-specific
2. `externalProductMappings` is shared across k3mart, gobiz, grabfood, bigseller -- adding GrabFood-only fields pollutes it
3. The existing `grabfoodPrice` and `isAvailable` on `externalProductMappings` can be migrated/synced

### Pattern 2: Photo Upload with Write-Back
**What:** Upload photo in simulator, store in Convex file storage, link back to menu product.
**When to use:** When admin uploads a photo for a GrabFood menu item.

```typescript
// Backend: generateUploadUrl (follow feedback module pattern)
export const generateUploadUrl = mutation({
  args: { token: v.string() },
  handler: async (ctx, args) => {
    await requireRole(ctx, args.token, ["admin"]);
    return await ctx.storage.generateUploadUrl();
  },
});

// Backend: save photo and write-back to menuProducts
export const savePhoto = mutation({
  args: {
    token: v.string(),
    menuItemId: v.id("grabfoodMenuItems"),
    storageId: v.id("_storage"),
  },
  handler: async (ctx, args) => {
    await requireRole(ctx, args.token, ["admin"]);
    const item = await ctx.db.get(args.menuItemId);
    if (!item) throw new Error("Menu item not found");

    // Save to grabfoodMenuItems
    await ctx.db.patch(args.menuItemId, {
      photoStorageId: args.storageId,
      updatedAt: Date.now(),
    });

    // Write-back: also save to menuProducts (future photo field)
    // This enables photos to flow from GrabFood simulator to internal products
    if (item.menuProductId) {
      await ctx.db.patch(item.menuProductId, {
        photoStorageId: args.storageId,
      });
    }
  },
});

// Frontend: upload flow
const generateUploadUrl = useMutation(api.grabfoodMenu.mutations.generateUploadUrl);
const savePhoto = useMutation(api.grabfoodMenu.mutations.savePhoto);

async function handlePhotoUpload(file: File, menuItemId: Id<"grabfoodMenuItems">) {
  const url = await generateUploadUrl({ token });
  const result = await fetch(url, { method: "POST", body: file, headers: { "Content-Type": file.type } });
  const { storageId } = await result.json();
  await savePhoto({ token, menuItemId, storageId });
}
```

### Pattern 3: Push-to-GrabFood Two-Step Flow
**What:** Batch update menu items on GrabFood, then notify to trigger sync.
**When to use:** When admin confirms changes and clicks "Push to GrabFood".

The GrabFood Partner API has two relevant endpoints:
1. **PUT /partner/v1/batch/menu** -- Update individual item fields (price, availability, stock)
2. **POST /partner/v1/merchant/menu/notification** -- CRITICAL: triggers GrabFood to re-sync menu

For adding new items, the full menu push (PUT /partner/v1/menu) would be needed, but the existing architecture uses the webhook-based GET /menu approach instead: GrabFood calls our GET /api/grabfood/menu endpoint to fetch the menu. So the flow is:
1. Admin edits items in simulator
2. Push: save all changes to `grabfoodMenuItems` table
3. For price/availability changes: call batch update API
4. Call menu notification to trigger GrabFood re-pull
5. Track sync status via menu-sync webhook (already implemented in Phase 27.1)

```typescript
// Push action pattern
export const pushMenuToGrabFood = action({
  args: {
    token: v.string(),
    merchantID: v.string(),
    changes: v.object({
      priceUpdates: v.array(v.object({ id: v.string(), price: v.number() })),
      availabilityUpdates: v.array(v.object({ id: v.string(), availableStatus: v.string() })),
    }),
  },
  handler: async (ctx, args) => {
    const accessToken = await resolveToken(ctx);
    if (!accessToken) return { success: false, error: "No GrabFood token" };

    // Step 1: Batch update prices (if any)
    if (args.changes.priceUpdates.length > 0) {
      await grabRequest(accessToken, "PUT", GRABFOOD_CONFIG.endpoints.menuBatch, {
        merchantID: args.merchantID,
        field: "PRICE",
        menuEntities: args.changes.priceUpdates,
      });
    }

    // Step 2: Batch update availability (if any)
    if (args.changes.availabilityUpdates.length > 0) {
      await grabRequest(accessToken, "PUT", GRABFOOD_CONFIG.endpoints.menuBatch, {
        merchantID: args.merchantID,
        field: "AVAILABILITY",
        menuEntities: args.changes.availabilityUpdates.map(u => ({
          id: u.id,
          availableStatus: u.availableStatus,
          ...(u.availableStatus === "UNAVAILABLE" ? { maxStock: 0 } : {}),
        })),
      });
    }

    // Step 3: MUST notify to trigger re-sync
    await grabRequest(accessToken, "POST", GRABFOOD_CONFIG.endpoints.menuNotify, {
      merchantID: args.merchantID,
    });

    return { success: true };
  },
});
```

### Pattern 4: Sync Status Tracking
**What:** After push, track the GrabFood sync job via the menu-sync webhook.
**When to use:** After any push to GrabFood.

The menu-sync webhook (POST /api/grabfood/menu-sync) is already implemented in Phase 27.1. It logs to `externalSyncLogs` with status success/error. The simulator can query recent sync logs to show status.

Alternatively, the trace endpoint (GET /partner/v1/merchant/menu/trace) can be polled to get `MenuSyncResponse` with `Code` (status), `CreatedTime`, `UpdatedTime`, and `Errors`.

**Recommendation:** Use a simple client-side polling approach:
1. After push, save a "push timestamp" in local state
2. Query recent sync logs (externalSyncLogs where source=grabfood, syncType=webhook, triggeredBy contains "menu-sync")
3. Show latest status badge: PENDING (just pushed) -> SUCCESS/FAILED (when webhook arrives)
4. Optional: call menu trace endpoint for more detail

### Pattern 5: "Sync Latest from GrabFood" (Pull Flow)
**What:** The primary entry point is pulling current menu state.
**When to use:** When admin clicks "Sync latest from GrabFood" button.

Since GrabFood Partner API has NO GET menu endpoint (confirmed in adapter.ts comments), "sync latest" means loading from our own `grabfoodMenuItems` table + `externalProductMappings`. The "ground truth" for what's live on GrabFood is what our GET /menu webhook serves.

If the `grabfoodMenuItems` table is empty (first use), the pull populates from `externalProductMappings` (source: grabfood) which were set up in Phase 27.1.

### Anti-Patterns to Avoid
- **Don't use PUT /partner/v1/menu for full menu replacement on every change** -- This replaces the entire menu structure. Use batch update for price/availability changes and rely on the webhook-based menu serving for new items.
- **Don't store GrabFood-specific data in `menuProducts` table** -- Keep internal product data separate from channel-specific overrides.
- **Don't forget the menu notification step** -- Changes via batch API are NOT live until POST /partner/v1/merchant/menu/notification is called.
- **Don't divide IDR prices by 100** -- IDR has exponent=0, so 25000 means Rp 25,000 (confirmed in Phase 27-01 decisions).

## Common Pitfalls

### Pitfall 1: IDR Price Handling
**What goes wrong:** Displaying or storing prices with decimal division (e.g., 25000/100 = 250).
**Why it happens:** GrabFood API uses "minor unit" pricing, but IDR has exponent=0 so 25000 IS Rp 25,000.
**How to avoid:** Store and display prices as integers. Use `formatCurrency` from `src/lib/utils.ts` for display.
**Warning signs:** Prices appearing as 1/100th of expected value.

### Pitfall 2: Missing Menu Notification After Batch Update
**What goes wrong:** Changes pushed via batch API but not visible on GrabFood app.
**Why it happens:** Batch updates are queued but NOT live until the notification POST is called.
**How to avoid:** Always call `POST /partner/v1/merchant/menu/notification` after any batch update. The existing `batchUpdateAvailability` action already does this.
**Warning signs:** Changes saved successfully in API response but not reflected on GrabFood within expected timeframe.

### Pitfall 3: MaxStock=0 Required for UNAVAILABLE
**What goes wrong:** Setting availableStatus to "UNAVAILABLE" without maxStock=0.
**Why it happens:** GrabFood API requires both fields to be set together for unavailability.
**How to avoid:** When toggling unavailable, always send `{ availableStatus: "UNAVAILABLE", maxStock: 0 }`. The existing `batchUpdateAvailability` action already handles this.
**Warning signs:** Items still appearing as available on GrabFood despite being toggled off.

### Pitfall 4: Convex Actions vs Mutations for API Calls
**What goes wrong:** Trying to call external APIs from mutations (which don't support fetch).
**Why it happens:** Confusing Convex actions (can fetch) with mutations (DB only).
**How to avoid:** All GrabFood API calls go through actions (in adapter.ts with "use node" directive). Mutations handle DB operations only.
**Warning signs:** Runtime errors about fetch not being available.

### Pitfall 5: Photo Upload File Size
**What goes wrong:** Uploading very large photos that slow down the GrabFood preview.
**Why it happens:** No client-side validation on file size.
**How to avoid:** Add client-side file size check (max 5MB) and optionally resize/compress before upload. GrabFood photo URLs in the sample JSON are standard web images (JPEG).
**Warning signs:** Slow loading of the menu preview page.

### Pitfall 6: Hooks Before Conditional Returns
**What goes wrong:** React hooks called after early returns (loading checks).
**Why it happens:** Common mistake when adding loading states.
**How to avoid:** All hooks MUST be called before any conditional returns. Check `if (data === undefined) return <Loading />` only after all hooks.
**Warning signs:** React hook order error in console.

## Open Questions

1. **Migration of existing externalProductMappings data**
   - What we know: Phase 27.1 created externalProductMappings with grabfoodPrice and isAvailable fields. The new grabfoodMenuItems table will duplicate some of this.
   - What's unclear: Should we migrate existing mappings to the new table on first load, or keep both tables and sync them?
   - Recommendation: On first "Sync latest" click, auto-populate grabfoodMenuItems from existing externalProductMappings. Keep externalProductMappings as the canonical mapping table (for revenue bridging), and grabfoodMenuItems as the simulator's working copy. The GET /menu webhook should read from grabfoodMenuItems if populated, falling back to externalProductMappings.

2. **Photo URL for GrabFood push**
   - What we know: Convex file storage generates URLs via `ctx.storage.getUrl(storageId)`. GrabFood items have a `photos: string[]` field.
   - What's unclear: Will GrabFood accept Convex storage URLs in the photos array? The URLs are public CDN URLs, so they should work.
   - Recommendation: Use Convex storage URL as the photo URL. Test with one item before bulk push.

3. **menuProducts.photoStorageId field**
   - What we know: The write-back pattern needs a `photoStorageId` field on `menuProducts`. This field doesn't exist yet.
   - What's unclear: Should we add it now or defer to the "Photo upload for internal menu products" deferred idea?
   - Recommendation: Add `photoStorageId: v.optional(v.id("_storage"))` to `menuProducts` schema now, as the write-back is a locked decision.

4. **Relationship between grabfoodMenuItems and the GET /menu webhook**
   - What we know: The webhook (Phase 27.1) currently builds menu JSON from externalProductMappings.
   - What's unclear: Should the webhook be updated to read from grabfoodMenuItems instead?
   - Recommendation: Yes -- update the GET /menu webhook to prefer grabfoodMenuItems (richer data: name overrides, descriptions, photos) with fallback to externalProductMappings for backward compatibility.
