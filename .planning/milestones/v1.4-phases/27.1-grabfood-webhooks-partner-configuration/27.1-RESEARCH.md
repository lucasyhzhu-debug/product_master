# Phase 27.1: GrabFood Webhooks & Partner Configuration - Research

**Researched:** 2026-02-26
**Domain:** GrabFood Partner API inbound webhooks, Convex httpAction, HMAC-SHA256 validation
**Confidence:** HIGH

## Summary

Phase 27.1 implements 6 inbound webhook endpoints for GrabFood Partner API integration, enabling the GrabFood App Simulator test cases to work end-to-end. The codebase already has 2 scaffolded webhook handlers (order + menu-sync) and a working HMAC validation function — but the HMAC secret is hardcoded to `undefined` and needs to be sourced from the `platformCredentials` table. Four new handlers need to be built (GET menu, order state, integration status, menu push), plus a frontend Webhooks tab.

The critical insight from CONTEXT.md is that this is a **passive integration** — webhooks observe and log only, they do NOT control the order lifecycle. The existing `upsertOrder` mutation should be removed (orders are not stored, only logged to syncLogs). All handlers follow the same pattern: validate HMAC, log key fields, write to syncLogs, return HTTP 200.

**Primary recommendation:** Implement all 6 handlers in the existing `convex/integrations/grabfood/webhooks.ts` with shared HMAC resolution from DB. Add `hmacSecret` to `platformCredentials` schema, add `"webhook"` to the `syncType` validator, and add per-mapping `grabfoodPrice` + `isAvailable` fields to `externalProductMappings`. Frontend gets a new Webhooks tab (separate from Settings) with HMAC secret field and copyable webhook URLs.

## User Constraints (from CONTEXT.md)

- All 6 handlers follow the same pattern: validate HMAC, console.log key fields, write to syncLogs table, return HTTP 200
- **No grabfoodOrders DB writes** — orders are not stored, only logged. The existing `upsertOrder` mutation should be **removed**

### Pattern 1: Webhook Handler Pattern (all 6 follow this)
**What:** Every webhook handler follows identical HMAC-validate-log-respond flow
**When to use:** All POST webhook handlers
**Example:**
```typescript
// Source: existing webhooks.ts pattern + CONTEXT.md decisions
export const handleXxxWebhook = httpAction(async (ctx, request) => {
  const body = await request.text();
  const signatureHeader = request.headers.get("X-Grab-Signature");
  const hmacSecret = await resolveHmacSecret(ctx);
  const hmacResult = await validateHmacSignature(body, signatureHeader, hmacSecret);

  // Always write to syncLogs (even failures)
  const status = (!hmacResult.valid && hmacResult.reason !== "no_secret") ? "error" : "success";

  let payload: any = {};
  try { payload = JSON.parse(body); } catch { /* invalid JSON */ }

  console.log(`GrabFood xxx webhook: ${JSON.stringify(payload).slice(0, 200)}`);

  try {
    await ctx.runMutation(internal.externalData.mutations.createSyncLog, {
      source: "grabfood",
      syncType: "webhook",
      status: status === "error" ? "error" : "success",
      timestamp: Date.now(),
      triggeredBy: "grabfood-webhook",
      ...(status === "error" ? { errorMessage: `HMAC failed: ${hmacResult.reason}` } : {}),
    });
  } catch (err) {
    console.log("Failed to write sync log:", err);
  }

  return new Response("OK", { status: 200 });
});
```

**When to use:** Only for the GET menu endpoint
**Example:**

export const handleGetMenuWebhook = httpAction(async (ctx, request) => {
  // HMAC on empty body for GET
  const signatureHeader = request.headers.get("X-Grab-Signature");
  const hmacSecret = await resolveHmacSecret(ctx);
  // ... validate ...

  // Query product mappings with joined menuProduct data

      availableStatus: "AVAILABLE",

      // ... other fields
    }));

  const menu = {
    merchantID: url.searchParams.get("merchantID") ?? "",

    sections: [{ id: "main", name: "Frollie Menu", categories: [{ id: "snacks", name: "Snacks", items }] }],

    status: 200,

### Anti-Patterns to Avoid
- **Writing to grabfoodOrders from webhooks:** CONTEXT.md explicitly says "No grabfoodOrders DB writes". Webhooks log to syncLogs only.
- **Using process.env in httpAction:** Non-Node runtime. The existing code has a TODO for this. Must use `ctx.runQuery` to fetch HMAC secret from DB.
- **Returning non-200 from webhooks:** GrabFood retries on non-200. Always return 200 per spec.
- **Outbound API calls from webhooks:** Never call order/prepare or auto-accept. This is passive.

## Common Pitfalls

### Pitfall 1: syncType "webhook" Not in Validator
**What goes wrong:** The existing `createSyncLog` mutation only accepts `syncType: "manual" | "cron" | "token_refresh"`. Passing `"webhook"` will throw a Convex validation error at runtime.
**Why it happens:** The impl plan doc uses `syncType: "webhook" as any` — casting to avoid the type error but this will fail at runtime because Convex validates args server-side.
**How to avoid:** Add `v.literal("webhook")` to both the `externalSyncLogs` schema table definition AND the `createSyncLog` mutation args validator BEFORE deploying webhook handlers.
**Warning signs:** Runtime "Invalid value for argument syncType" errors in Convex logs.

### Pitfall 2: Removing upsertOrder Breaks Existing Sync Flow
**What goes wrong:** The `upsertOrder` mutation is called by both the webhook handler AND the `syncOrders` action (via `upsertOrderBatch`). Removing it breaks order sync.
**Why it happens:** CONTEXT.md says "remove upsertOrder" but the sync action still needs it.
**How to avoid:** Only remove the webhook's call to `upsertOrder` (in `handleOrderWebhook`). Keep `upsertOrder` and `upsertOrderBatch` alive for the outbound sync flow (`adapter.ts:syncOrders`). The webhook handler should log to syncLogs instead.
**Warning signs:** `syncOrders` action fails after deployment.

### Pitfall 3: externalProductMappings Lacks Price/Availability Fields
**What goes wrong:** CONTEXT.md requires per-mapping GrabFood price and availability toggle, but `externalProductMappings` schema only has: `source, externalProductCode, externalProductName, menuProductId, isAutoMapped, createdAt`.
**Why it happens:** These fields were never needed until the GET /menu endpoint needed platform-specific pricing.
**How to avoid:** Add `grabfoodPrice: v.optional(v.number())` and `isAvailable: v.optional(v.boolean())` to the `externalProductMappings` table schema. Update the Settings tab mutation to save these fields.
**Warning signs:** GET /menu always returns internal prices with no way to override.

### Pitfall 4: httpAction Cannot Call "use node" Functions Directly
**What goes wrong:** Attempting to import from adapter.ts (which is `"use node"`) in webhooks.ts (which is not) causes build failures.
**Why it happens:** Convex separates Node and non-Node runtimes. httpAction handlers run in the non-Node (V8) runtime.
**How to avoid:** webhooks.ts must only import from `_generated/server`, `_generated/api`, and other non-`"use node"` files. Use `ctx.runQuery`/`ctx.runMutation`/`ctx.scheduler.runAfter` with `internal.*` references to call into Node functions indirectly.
**Warning signs:** Build errors about importing "use node" modules.

### Pitfall 5: Missing serviceHours in Menu JSON
**What goes wrong:** GrabFood App Simulator rejects menu JSON missing the `serviceHours` field in sections.
**Why it happens:** The GrabFood sample menu JSON shows `serviceHours` as a required field on sections with per-day open period configuration.
**How to avoid:** Include full `serviceHours` object in the section with all 7 days set to "00:00"-"23:59" OpenPeriod (matching the impl plan approach).
**Warning signs:** App Simulator test cases #1-5 fail with validation errors.

### Pitfall 6: HMAC Validation on GET Requests
**What goes wrong:** GET /menu has no body, so HMAC is computed on empty string. If GrabFood computes HMAC differently for GET (e.g., on query params), validation fails.
**Why it happens:** HMAC spec says "raw_body_bytes" but GET has no body.
**How to avoid:** For GET requests, validate HMAC on empty string `""`. If that fails, try validating on the full URL query string. The existing `validateHmacSignature` function already handles empty string. If HMAC secret is not configured, validation is skipped entirely (returns true with reason "no_secret").
**Warning signs:** GET /menu returns HMAC failure even with correct secret configured.

// Source: project pattern from platformCredentials/queries.ts
export const getHmacSecret = internalQuery({
  args: { platformId: v.string() },
  handler: async (ctx, args) => {
    const cred = await ctx.db
      .query("platformCredentials")
      .withIndex("by_platform", (q) => q.eq("platformId", args.platformId))
      .first();
    return cred?.hmacSecret ?? null;
  },
});

### Save HMAC Secret Mutation
```typescript
// New dedicated mutation for HMAC secret (separate from saveCredentials which handles email/password)
export const saveHmacSecret = mutation({
  args: {
    token: v.string(),
    platformId: v.string(),
    hmacSecret: v.string(),
  },
  handler: async (ctx, args) => {
    const user = await requireRole(ctx, args.token, ["admin"]);
    const existing = await ctx.db
      .query("platformCredentials")
      .withIndex("by_platform", (q) => q.eq("platformId", args.platformId))
      .first();

    if (existing) {
      await ctx.db.patch(existing._id, { hmacSecret: args.hmacSecret, updatedBy: user.name, updatedAt: Date.now() });
      return existing._id;
    }
    // Create new credential record with only hmacSecret
    return await ctx.db.insert("platformCredentials", {
      platformId: args.platformId,
      hmacSecret: args.hmacSecret,
      updatedBy: user.name,
      updatedAt: Date.now(),
    });
  },
});
```

## Open Questions

1. **HMAC on GET requests — what does GrabFood sign?**
   - What we know: POST webhooks sign the raw body. GET has no body.
   - What's unclear: Does GrabFood compute HMAC on empty string, query string, or full URL for GET?
   - Recommendation: Try empty string first (existing function handles this). If simulator fails, try query string. LOW risk since HMAC is skipped when no secret configured.

2. **Should upsertOrder be fully removed or just disconnected from webhook?**
   - What we know: CONTEXT.md says "remove upsertOrder". But `syncOrders` action calls `upsertOrderBatch` which uses similar logic.
   - What's unclear: Does "remove" mean the single-order mutation specifically, or all order storage?
   - Recommendation: Remove the webhook's call to `upsertOrder` in `handleOrderWebhook`. Keep `upsertOrder` and `upsertOrderBatch` alive for the outbound sync flow. The CONTEXT.md intent is "webhooks don't write orders", not "delete all order storage".

3. **Menu JSON: sellingTimes field required?**
   - What we know: The sample menu JSON includes `sellingTimes` at top level and `serviceHours` per section.
   - What's unclear: Whether App Simulator validates `sellingTimes` presence.
   - Recommendation: Include `sellingTimes` with a single "All Day" entry (00:00-23:59) to match the sample. Include `serviceHours` per section. LOW risk.
