<objective>
Prune `getKitchenStats` intermediate data to reduce per-call payload from ~35 KB.

Purpose: `getKitchenStats` consumes 25 MB at 742 calls. The subscription MUST stay reactive (kitchen needs live updates). The optimization is purely payload reduction. The query currently fetches full `Doc<"orderItemProduction">` objects into maps but only uses numeric fields (`unitsRemaining`, `unitsCompleted`, `productionUnitCode`, `productionUnitTypeId`, `isCancelled`). The full Doc includes `orderId`, `orderItemId`, `productName`, `variant`, timestamps etc. that are never used in the aggregation.

However, the Convex DB query returns full documents — there's no projection. The key optimization: ensure the RESPONSE (return value) doesn't contain any full Doc objects. Currently the return is already aggregated numbers — verify this and optimize if any leakage exists.

Output: Verified/optimized query return shape.
</objective>

**Optimization: Skip item+production lookups for Draft and AwaitingPayment orders.**

**NOTE on status names:** CLAUDE.md documents the workflow as Draft -> AwaitingPayment -> Confirmed -> InProduction -> Boxed -> Labeled -> etc. However, the **actual status strings in the codebase** (see `convex/orders/queries.ts` and `convex/integrations/internal/config.ts`) are: `Draft`, `AwaitingPayment`, `PaymentReceived`, `BeingPrepared`, `AwaitingDelivery`, `Complete`. The existing `getKitchenStats` query already uses these actual status strings. Use the ACTUAL code values, not the CLAUDE.md documentation names.

Production records (`orderItemProduction`) are created at confirmation time (status = `PaymentReceived`), NOT at Draft or AwaitingPayment time. Therefore Draft and AwaitingPayment orders **never** have `orderItemProduction` records. Fetching their items and production data is pure waste.

The existing `getKitchenStats` code (lines 618-624) ALREADY separates the status groups:
```typescript
const [draftOrders, awaitingPaymentOrders, paymentReceivedOrders, beingPreparedOrders] = await Promise.all([...]);
const pendingOrders = [...draftOrders, ...awaitingPaymentOrders, ...paymentReceivedOrders, ...beingPreparedOrders];
```

But then at line 636 it includes ALL pendingOrders in `relevantOrders` for item+production lookups:
```typescript
const relevantOrders = [...pendingOrders, ...completedTodayOrders];
```

**Fix:** Change line 636 to exclude Draft and AwaitingPayment orders from the expensive lookups:

```typescript
// Only fetch items/production for orders that actually have production records
// Draft and AwaitingPayment orders have NO orderItemProduction records — skip them
const productionOrders = [...paymentReceivedOrders, ...beingPreparedOrders];
const relevantOrders = [...productionOrders, ...completedTodayOrders];
const relevantOrderIds = [...new Set(relevantOrders.map((o) => o._id))];
```

The `pendingOrders` array (which includes Draft + AwaitingPayment) is still used for the `ordersPending` count — just not for the nested item/production lookups. This eliminates all DB reads for Draft/AwaitingPayment order items and production records.
